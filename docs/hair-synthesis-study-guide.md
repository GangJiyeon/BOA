# BOA 헤어스타일 합성 학습 가이드

2026-11-20 로컬 코드 기준.

회원 기능 가이드와 같은 방식으로 **사용자 행동 → API → AI 생성 → 영상 후처리 → 파일·DB → 브라우저 염색**을 설명한다. 기존 주석·문서의 구현 이유와 현재 코드 동작을 구분한다. 이 문서 작성 중 유료 AI 요청이나 실제 얼굴 사진 전송은 수행하지 않았다.

- **[기록/주석]**: 기존 문서 또는 코드 주석에 직접 적힌 이유.
- **[코드 확인]**: 현재 구현에서 확인한 동작.
- **[해설/추론]**: 원리를 이해하기 위한 설명. 작성자의 확정된 의도와 구분한다.

## 1. 가장 먼저 이해할 구조

이 기능은 카탈로그 사진의 머리를 잘라서 사용자 사진에 그대로 붙이는 방식이 아니다. **AI가 사용자의 새로운 헤어스타일을 생성하고, 서버가 원본 얼굴과 생성 결과를 다시 합성한 뒤, 브라우저가 머리색을 바꾼다.**

```text
사용자 정면 사진 + 원하는 스타일
                 ↓
서버: 얼굴·각도·크기 검사
                 ↓
원본 한 장을 출력 비율에 맞게 패딩
                 ↓
Google 이미지 편집 AI 한 번 호출
                 ↓
중간 갈색 헤어스타일 한 장 생성
                 ↓
서버: 구도 검사 → 원본에 정렬 → 얼굴 보존 합성 → 머리 마스크 생성
                 ↓
brown.jpg + brown_mask.png 저장
                 ↓
브라우저에서 갈색 베이스의 머리 영역을 Lab으로 색 변경
                 ↓
색상 프리셋·이미지 다운로드
```

여기에는 서로 다른 세 작업이 있다.

| 작업 | 담당 | 새 AI 요청 |
|---|---|---|
| 헤어스타일 변경 | Google 이미지 편집 모델 | 새 합성을 시작할 때 1회 |
| 원본 얼굴 보존·생성 결과 정렬·마스크 | 서버 OpenCV·MediaPipe | 없음 |
| 생성된 스타일의 머리색 변경 | 브라우저 Canvas·TypeScript | 없음 |

따라서 “32색을 고를 때마다 AI를 32번 부른다”거나 “얼굴형 추천 알고리즘이 합성 이미지도 만든다”고 이해하면 안 된다.

## 3. 사용자 진입: 추천을 받아야만 합성할 수 있는가?

현재는 두 경로가 있다.

### 3.1 직접 업로드·카탈로그 선택

정면 사진을 올리고, 전체 카탈로그에서 성별 구분·길이·질감을 필터링해 스타일을 고른다. 얼굴형 추천을 먼저 하지 않아도 된다. 이 경우 `run_id`를 보내지 않는다.

### 3.2 헤어 추천에서 가져오기

상위 화면이 보관 중인 `HairSessionResult`에서 다음을 가져온다.

- 헤어 추천 목록과 실행 번호 `run_id`.
- 얼굴형 분석 정보.
- 얼굴형 분석에 사용한 사진 중 정면 사진 `File`.
- 이미 계산된 머리색 추천이 있으면 그 결과.

[코드 확인] 원본 File은 브라우저 메모리에서 전달된다. DB의 분석 번호만으로 원본 사진을 복원하는 기능이 아니다. 페이지를 새로고침하면 이 메모리 사진을 잃을 수 있어 직접 업로드 경로가 중요하다.

사진·스타일·모드를 바꾸면 `clearResult()`가 이전 결과를 지운다. 생성 중에는 입력을 제한하고 `useTask()`로 중복 제출과 화면 이탈 시 응답 처리를 관리한다.

## 4. 요청과 응답: 왜 202와 폴링을 쓰는가?

### 4.1 생성 요청

```text
POST /api/studio/hair-renders
Content-Type: multipart/form-data

photo    : 사진 File
style_id : 선택한 카탈로그 스타일 번호
run_id   : 추천에서 가져온 경우에만 포함
```

사진은 바이너리이므로 JSON 대신 FormData로 전송한다. 공통 API 클라이언트는 FormData의 Content-Type 경계를 브라우저가 만들도록 둔다.

### 4.2 백엔드 처리 순서

1. `require_analysis_actor`로 회원·동의한 비회원·사용자 세션이 있는 키오스크인지 검사.
2. Gemini API 키가 없으면 503.
3. 스타일이 없으면 404.
4. run_id를 보냈다면 해당 추천 실행이 존재하는지 검사.
5. `quota.check_quota(..., 'studio')`로 비회원 사용량 검사.
6. 사진을 읽고 10MB 초과면 413.
7. 이미지 디코딩·얼굴 조건 검사. 부적합하면 422.
8. `HairRender` 행을 pending 상태로 저장·커밋.
9. `BackgroundTasks`에 `process_render(render.id, photo_bytes)` 등록.
10. 작업 정보와 번호를 202로 응답.

[해설] 202는 “합성이 완성됐다”가 아니라 “작업을 받아들였다”는 뜻이다. 사진 조건 검사는 이 응답 전 동기적으로 수행하므로 초기 요청 자체가 완전히 즉시 끝나는 구조는 아니다.

### 4.3 상태 조회

```text
GET /api/studio/hair-renders/{id}

pending → 처리 중
 done   → 이미지와 마스크 사용 가능
 failed → 오류 안내
```

프론트는 2초 간격으로 최대 90회 조회한다. 단순 대기 시간 합계는 약 180초이고 각 HTTP 요청 시간은 별도로 더해진다. 초과하면 사용자에게 오래 걸린다는 오류를 보여준다.

[코드 확인] 화면 대기 종료나 요청 취소가 이미 실행 중인 서버·Google 작업을 취소하는 API는 없다. 브라우저가 기다리지 않아도 서버 작업이 계속될 수 있다.

대기 화면의 “사진 인식 → AI 머리 합성 → 얼굴 맞춤 → 마무리” 문구는 **서버가 보고한 실제 세부 진행률이 아니라 경과 시간에 따른 안내**다.

## 5. 사진을 AI에 보내기 전에 검사하는 이유

`decode_image()`는 이미지를 OpenCV BGR 배열로 읽고 긴 변을 최대 1024px로 줄인다. 검사는 축소된 이미지에 적용된다.

| 검사 | 현재 기준 | 이유 |
|---|---|---|
| 디코딩 | 읽을 수 있는 이미지인가 | 손상·이미지 아닌 데이터 차단 |
| 얼굴 검출 | FaceMesh로 얼굴을 찾는가 | 정렬할 기준점 필요 |
| 좌우 기울기 roll | 절댓값 10° 이하 | AI가 자세를 세우면서 구도를 바꾸는 문제 |
| 좌우 돌림 yaw 지표 | 절댓값 0.35 이하 | 측면 사진의 얼굴 재생성·정렬 실패 줄이기 |
| 얼굴 폭 | 120px 이상 | 가닥·눈썹과 윤곽 처리에 필요한 해상도 |

[기록/주석] 유료 AI를 호출한 뒤 실패를 발견하면 비용과 시간을 이미 사용한다. 가능한 입력 오류를 먼저 거르는 설계다.

roll은 두 눈꼬리를 잇는 선의 각도다. yaw는 실제 3D 회전 각도가 아니라 코끝의 가로 위치를 두 눈꼬리 사이에서 정규화한 **측면 회전의 근사 지표**다. 0.35를 0.35°로 읽으면 안 된다.

`max_num_faces=1`로 첫 얼굴을 처리하므로 여러 사람이 찍혔는지를 별도 검사하는 구조는 아니다. `generate()`도 prepare_photo를 다시 호출한다. 요청 진입 검사와 생성 서비스의 독립 검사가 중복되는 형태다.

## 6. MediaPipe의 두 역할을 구분하기

### 6.1 FaceMesh: 점을 찾는다

`landmarks()`는 눈·코·턱·눈썹 등의 픽셀 좌표를 얻는다. 회전·크기·윤곽·보호 영역의 기준이 된다. 얼굴 모양을 새로 생성하는 모델은 아니다.

### 6.2 Selfie multiclass segmenter: 영역 확률을 찾는다

`segment()`는 다음 확률 지도를 반환한다.

```text
hair : 머리카락일 확률
face : 얼굴 피부일 확률
bg   : 배경일 확률
body : 몸 피부일 확률
```

분할 모델은 `selfie_multiclass_256x256.tflite`이고 최초 사용 시 파일이 없으면 내려받는다. CPU delegate를 사용한다. 저해상도 확률 지도를 원본 크기로 확대해 사용하므로 가는 앞머리의 세부 정보가 부족할 수 있다.

[기록/주석] 공유 MediaPipe 그래프는 스레드 안전하지 않아 `_lock`으로 추론을 보호한다. 네트워크 AI 호출 전체를 이 잠금으로 묶는 구조는 아니다.

## 7. 스타일 참조 사진을 왜 가리는가?

`_style_ref()`는 카탈로그 이미지가 `/static/`으로 시작하는 로컬 파일일 때 참조 JPEG를 만든다. URL이 외부 주소거나 파일이 없으면 텍스트 설명만 사용한다.

### 7.1 배경은 흰색으로

[기록/주석] 카탈로그를 표에서 잘라낸 이미지에 옆 칸 이름표가 섞였고, “Flower perm” 글자 때문에 원래 생머리 스타일이 곱슬로 생성된 사례가 있었다. 그래서 인물 바깥 배경을 흰색으로 정리한다.

### 7.2 얼굴 피부는 회색으로

[기록/주석] 선명한 참조 얼굴이 있으면 AI가 머리뿐 아니라 참조 모델의 얼굴·구도까지 따라 그려 사람이 바뀌었다. 회색 마스킹은 참조 이미지에서 머리 정보만 가져오게 유도하기 위한 것이다.

다만 이마까지 가리면 앞머리 정보도 사라진다. 현재는 랜드마크로 경계를 잡아 **눈썹 아래쪽의 얼굴 피부를 중심으로 가리고, 이마와 앞머리 정보는 남긴다.**

[해설] 이 회색 마스킹은 참조 역할을 분리하기 위한 전처리다. 익명화나 얼굴 식별 불가능성을 보장하는 처리로 설명하면 안 된다.

## 8. 프롬프트: 사진과 텍스트의 역할 분리

`style_prompt()`는 스타일 이름·성별 구분·길이·질감·guide를 조합하고, 참조 사진 유무에 따라 지시를 바꾼다.

### 8.1 첫 번째 이미지와 두 번째 이미지

- 첫 번째 이미지: **사용자 정체성·해부학적 얼굴 구조·포즈·구도**의 기준.
- 두 번째 이미지: **새 헤어스타일의 길이·외곽·층·가르마·앞머리·컬·볼륨**의 기준.
- 참조의 얼굴·체형·배경·머리색은 가져오지 않도록 지시.
- 참조가 있으면 텍스트는 스타일을 식별하고 참조는 모호한 이름과 대략적인 길이 분류를 보완.

현재 프롬프트는 원래 헤어스타일 자체를 고정하지 않는다. 단순 염색이나 정리가 아니라 목표 헤어스타일로 바꾸도록 명시한다.

### 8.2 FACE_LOCK과 FRAME_LOCK

`FACE_LOCK`은 눈·코·입·얼굴 폭·턱·피부톤·메이크업을 바꾸지 말라는 규칙이다. AI가 V라인이나 미용 보정을 하는 현상을 줄이려는 지시다.

`FRAME_LOCK`은 얼굴 크기·카메라 거리·크롭·위치·표정·어깨 위치를 유지하라는 규칙이다. 새 머리가 커졌다고 인물을 작게 하거나 아래로 옮기는 결과를 줄이려는 지시다.

[해설] 프롬프트의 “LOCK”은 강제되는 소프트웨어 잠금이 아니다. AI가 반드시 준수한다는 보장은 없어서 생성 결과 검사와 픽셀 후처리가 별도로 필요하다.

### 8.3 길이와 질감의 충돌 방지

길이 규칙은 성별 구분과 short/medium/long 조합에 따라 다르다. 남성 short/medium을 선택한 경우 피사체가 여성처럼 보여도 단발로 길게 바꾸지 않도록 강조한다. 남성 long에는 묶음·브레이드·아프로 같은 목표 형태를 불필요하게 없애지 않도록 한다.

현재는 의도된 곱슬·컬·시스루 가닥을 보존하고, 모든 스타일을 매끈한 긴 곡선이나 두꺼운 앞머리로 강제하지 않는다. 과거 guide에 남아 있는 “참조의 질감보다 설명을 우선”하는 특정 문장은 새 참조 규칙과 충돌하므로 제거한다.

## 9. AI 입력과 출력의 크기 맞추기

`_pad_input()`은 원본 한 장에 AI가 지원하는 출력 비율에 맞는 패딩을 넣는다. 복사한 가장자리의 줄무늬를 AI가 따라 그리지 않도록 패딩 영역만 흐리게 한다.

요청 한 번으로 중간 갈색 베이스 한 장을 1K로 생성한다. `_crop_output()`은 생성 이미지를 패딩을 포함한 입력 크기로 맞춘 뒤 원래 입력 영역만 남긴다.

## 10. Google 이미지 편집 호출의 실제 동작

`gemini_image.edit_image()`는 JPEG 바이트를 base64로 바꾸고 텍스트 프롬프트와 함께 REST 요청한다.

```text
POST .../models/{설정된모델}:generateContent
인증 헤더: x-goog-api-key
입력: 패딩을 적용한 사용자 사진 + 선택적 참조 이미지 + 프롬프트
출력 요청: IMAGE, aspectRatio, imageSize=1K
```

현재 기본 모델 문자열은 `gemini-3.1-flash-image`다. `STUDIO_STYLE_MODEL`로 바꿀 수 있다. 이는 코드에 적힌 설정을 설명하는 것이며 외부 서비스의 최신 모델 지원 여부를 별도로 검증한 것은 아니다.

HTTP 기본 timeout은 180초다. HTTP 오류·200 아닌 응답·이미지 없는 응답을 `ImageGenError`로 바꾼다. 후보 중 첫 candidate의 parts를 돌며 처음 찾은 이미지 데이터를 반환한다. 이미지가 없으면 안전 필터 등으로 빈 응답이 된 경우를 포함해 실패 처리한다.

[코드 확인] 생성 요청의 자동 재시도는 없다. [기록/주석] 재시도하면 대기 시간이 2분 이상 늘어나는 문제 때문에 한 번만 호출하기로 했다. 실패 판정을 내려도 이미 사용한 외부 AI 호출 비용이 자동 취소되는 구조는 아니다.

## 11. 생성 결과를 그대로 보여주지 않는 이유

AI는 프롬프트를 지켜도 얼굴을 조금 작게·크게 하거나 턱을 좁히고 눈썹·표정을 바꿀 수 있다. 따라서 원본과 생성 결과의 관계를 검사한다.

`_generation_issue()`의 현재 기준:

| 검사 | 실패 기준 |
|---|---|
| 생성 얼굴 | 검출 불가 |
| 정렬 | 변환 추정 실패 |
| 크기 | 추정 스케일이 1에서 0.12 초과 차이 |
| 기울기 차이 | 원본 대비 4° 초과 |
| yaw 지표 차이 | 0.15 초과 |
| 정렬 후 유효 영역 | 원본 넓이의 80% 미만 |

[기록/주석] 정상·실패 생성 사례를 측정해 경계값을 조정했다. 이 수치를 다양한 인종·연령·촬영 조건 전체에 대해 검증된 보편 정확도로 해석하면 안 된다.

크기 검사는 `estimateAffinePartial2D`로 AI 얼굴을 원본에 맞추는 변환의 스케일을 기준으로 한다. “얼굴 픽셀 넓이가 정확히 12% 증가했는가”와 동일한 공식은 아니다.

검사 실패 시 사용자에게 다른 정면 사진을 안내하고 작업을 failed로 저장한다. 실패 작업은 비회원 사용량에서 제외한다. 품질 검사는 자세·정렬 중심이며, 원하는 스타일을 얼마나 정확히 재현했는지 자동 점수화하는 검사는 아니다.

## 12. 원본 얼굴에 새 머리를 붙이는 transplant_hair()

이 함수가 로컬 영상 처리의 핵심이다. AI 결과 전체를 그대로 최종 사진으로 쓰지 않고 원본과 섞는다.

### 12.1 얼굴 기준 정렬

`overlap_matrix()`는 원본과 생성 사진의 얼굴 랜드마크 468개로 이동·회전·균일한 크기 차이를 맞춘다. `fit_ai()`는 정렬한 얼굴의 광대 폭과 눈에서 턱까지의 길이를 원본과 비교해 합성 가능한 결과인지 검사한다.

## 13. 합성 마스크와 원본 얼굴 보호

### 13.1 새 머리만 붙이면 왜 부족한가?

긴 원래 머리를 단발로 바꿀 때 새 단발만 얹으면 어깨의 원래 긴 머리가 남는다. 그래서 합성할 AI 영역에는 다음이 포함된다.

- 새 머리.
- 원래 머리가 있던 자리 중 보호할 얼굴 피부를 제외한 부분.
- 앞머리 재구성에 필요한 이마 일부.
- 새로 드러난 목·어깨·옷 등 턱 아래 영역.

따라서 “최종 결과에서 AI가 바꾼 픽셀은 머리카락뿐”이라는 설명은 엄밀히는 틀리다.

### 13.2 얼굴 보호 영역과 앞머리

- 얼굴 윤곽 안에서 눈썹 조금 위부터 턱까지 원본을 우선한다.
- 기존 머리가 가렸던 얼굴 피부는 AI 결과로 채운다. 분할이 놓친 얇은 가닥은 주변 피부나 같은 줄의 픽셀로 메운다.
- 눈썹은 원본을 우선한다. 기존 앞머리가 많이 가린 눈썹은 생성 이미지의 눈썹을 원본 위치에 맞춰 쓴다.
- 새 머리가 얼굴에 겹치는 곳은 생성 이미지 쪽 가중치를 높인다.

### 13.3 다중 해상도 블렌딩

원본 보존 마스크가 1에 가까우면 원본 비중이 높고, 0에 가까우면 AI 비중이 높다. `_pyramid_blend()`는 낮은 해상도에서 색과 조명 경계를 넓게 섞고, 높은 해상도에서 머리 가닥과 피부 질감을 좁게 잇는다.

## 14. 피부·목·배경 톤을 따로 맞추는 이유

| 함수 | 처리 |
|---|---|
| `_match_skin_tone` | 원본·AI 둘 다 보이는 피부의 Lab 중앙값 차이로 피부 톤 보정. 볼 우선, 부족하면 이마 |

## 15. 정렬 후 가장자리 크롭

`compose_bases()`는 생성된 갈색 결과를 원본 위에 합성하고 염색 마스크를 만든다. `_valid_box()`는 정렬 후 실제 생성 픽셀이 남아 있는 직사각형을 구한다. 가장자리를 잘라야 할 때는 보간 경계를 피하도록 2px 여유를 둔다. 이미지와 마스크에는 같은 크롭을 적용한다.

## 16. 염색 마스크 만들기

합성 마스크는 원본과 AI를 섞는 비율이고, 염색 마스크는 합성 후 머리색을 바꾸는 강도다. 서버는 염색 마스크를 `brown_mask.png`로 저장한다.

`hair_mask()`는 머리 분할 확률을 부드럽게 처리한다. `base_hair_mask()`는 `see_through_strands()`가 찾은 가는 가닥을 더한다. 이 함수는 주변 피부와 픽셀의 밝기 차이를 사용하며, 검출 범위를 눈썹을 제외한 이마 주변으로 제한한다. `soften_fringe()`는 앞머리 끝의 염색 강도를 최대 25% 낮춘다.

## 17. 브라우저 염색 준비: prepareBase()

`HairColorStudio`는 베이스 이미지 한 장과 같은 크기의 마스크를 불러온다.

`prepareBase()`는 매번 색을 바꿀 때 반복하지 않도록 다음을 미리 계산한다.

- 원본 RGBA 픽셀.
- 모든 픽셀의 Lab 값.
- PNG의 빨간 채널을 255로 나눈 염색 알파.
- 마스크가 0.6보다 큰 머리 픽셀의 가중 평균 Lab.

마스크 0은 염색 안 함, 1은 강하게 적용, 중간값은 부드럽게 적용한다. PNG 파일의 투명도 채널을 읽는 것이 아니라 **흑백 마스크 이미지의 밝기 채널**을 사용한다.

[해설] CPU 계산을 앞에서 한 번 하고 색 변경 때 재사용하는 구조다. 현재 이 렌더러는 브라우저 JS·Canvas에서 실행하며 헤어 염색을 Web Worker나 GPU shader로 처리하는 코드는 아니다.

## 18. 브라우저에서 사용할 베이스

새 결과는 `brown` 한 쌍을 사용한다. 과거 결과의 호환 순서는 `brown` → `light` → `mid`다. 모든 프리셋과 추천색은 같은 이미지와 마스크에 적용된다.

## 19. renderColor(): 단색 덧칠과 다른 점

### 19.1 왜 Lab인가?

[해설] RGB 세 채널에 같은 값을 더하면 밝기와 색이 얽혀 조절하기 어렵다. Lab은 밝기 L*와 색도 a*·b*를 나눠 목표색으로 이동하면서 원래 가닥의 밝고 어두운 차이를 보존하기 편하다.

단순화한 핵심은 다음과 같다.

```text
새 밝기 ≈ 목표 밝기 + (현재 픽셀 밝기 − 머리 평균 밝기) × 명암 계수
새 색도 ≈ 목표 색도 + 원본 머리의 작은 색도 변동
```

모든 픽셀을 목표 hex로 똑같이 만들지 않으므로 머리결과 윤기를 남길 수 있다.

### 19.2 명암과 채도 처리

- 목표색·베이스 밝기에 따라 명암 계수를 조절한다.
- 밝은 베이스를 어둡게 내릴 때 결까지 지나치게 죽지 않도록 명암을 유지한다.
- 아주 어두운 목표색(L*<25)은 밝은 윤기 차이는 남기고 어두운 그림자 차이는 절반으로 줄인다.
- 밝기 상단·하단을 딱 잘라내지 않고 부드러운 함수로 압축한다.
- 극단적으로 밝거나 어두운 곳은 채도를 완화한다.
- 밝은 베이스의 반투명 경계는 배경과 섞여 있어 검은 외곽선이 생기지 않게 명암 차이를 줄인다.

`tex`는 명암·질감 계수, `vari`는 원본 색도 변동 반영량이다. `lOff`는 목표 밝기 이동, `chroma`는 목표 색도 배율이다. 현재 프리셋은 일부 tex·vari를 따로 조정하고, 기본값은 lOff=0/chroma=1/tex=1/vari=0.4다.

### 19.3 목표색 평균 1회 보정

실제로 칠해 RGB로 변환하면 채도 완화·밝기 압축·RGB 표현 범위 잘림 때문에 평균색이 목표에서 벗어날 수 있다. 그래서 머리 픽셀을 샘플링해 결과 Lab 평균과 목표 차이를 구하고 한 번 보정한다. 보정량은 채널별 ±30으로 제한한다.

코드의 `MATCH_STEP=8`은 평탄화된 픽셀 인덱스를 8씩 건너뛰는 샘플링이다. 가로·세로 각각 8px짜리 2D 격자를 의미하지는 않는다.

주석의 “평균 오차 1.0, 최대 3.3, 약 13ms”는 당시 특정 실험의 기록이다. 전체 사용자 사진과 기기에서 보장되는 정확도·속도는 아니다.

### 19.4 마지막 합성

```text
표시 RGB = 베이스 RGB × (1 − 염색 알파) + 염색 RGB × 염색 알파
```

마스크가 거의 0인 배경·얼굴은 베이스 픽셀을 유지한다. 마스크가 잘못됐으면 좋은 색 변환식으로도 피부 착색을 완전히 막을 수 없다.

## 20. 프리셋·원래 머리색·비교·저장

### 20.1 32색 프리셋

팔레트는 블랙, 브라운, 애쉬, 레드, 핑크·퍼플·블루 그룹의 32색으로 구성한다.

### 20.2 원래 머리색

서버 `hair_hex()`는 머리 확률 0.8 초과 픽셀이 500개 이상일 때 Lab 중앙값을 hex로 저장한다. 없으면 null이다.

프론트의 “원래 머리색”은 **새 헤어스타일을 그 대표 색으로 염색**하는 버튼이다. 원래 헤어스타일·부분 염색·하이라이트·염색 전 사진을 통째로 복원하는 기능은 아니다.

### 20.3 누르는 동안 염색 전 보기

현재 선택한 베이스의 `src` 픽셀을 보여준다. 즉 새로 합성한 스타일의 해당 베이스 색을 보여주는 비교이지, 합성 전 사용자 원본 사진과의 비교는 아니다. 기본 색으로 버튼은 불러온 베이스의 색으로 돌아간다.

### 20.4 이미지 저장

Canvas를 PNG data URL로 만들고 브라우저 다운로드를 실행한다. 사용자가 고른 모든 색 조합을 서버 DB에 따로 저장하는 API는 없다.

## 21. 피부 명도 기반 머리색 추천과 합성의 관계

`recommendHairColors()`는 피부 명도와 팔레트 색의 Lab 밝기 차이를 구한다. 차이 12·28·44에 가까운 색을 중복 없이 고르고 부드러운·중간·선명한 대비라는 이름을 붙인다.

[코드 확인] 이 결과가 현재 합성에 사용한 추천 사진과 연결될 때만 `HairColorStudio`에 전달된다. 직접 업로드한 임의 사진에 이전 사람의 추천색이 붙지 않도록 조건을 둔다.

이 로직은 명도 대비를 비교하는 선택 보조다. 퍼스널컬러 전문 진단이나 웜·쿨톤 검증, 실제 미용실 염색 결과 예측 모델과는 다르다. 헤어스타일 추천 점수와 머리색 추천도 별도 계산이다.

## 22. DB·파일·개인정보의 생명주기

### 22.1 HairRender 한 행의 의미

| 필드 | 의미 |
|---|---|
| id | 생성 작업 번호 |
| user_id / guest_id | 작업 소유자 |
| run_id | 선택적으로 연결한 헤어 추천 실행 |
| style_id | 합성 대상 카탈로그 스타일 |
| status | pending/done/failed |
| error | 실패 메시지, 최대 300자 |
| asset_dir | 무작위 결과 폴더 이름 |
| hair_hex | 원본에서 추정한 대표 머리색 |
| created_at / finished_at | 요청·종료 시각 |

`process_render()`는 요청용 DB 세션과 별도로 자체 세션을 연다. 생성·파일 저장이 끝나면 done, 알려진 실패는 failed와 메시지, 예상 밖 예외는 로그와 일반 메시지를 저장한다.

### 22.2 파일

```text
static/studio/{무작위 asset_dir}/
  brown.jpg    brown_mask.png
```

`asset_dir`는 `secrets.token_urlsafe(24)`다. 완료 응답은 각 JPG·PNG의 URL과 hair_hex를 제공한다. 과거 결과의 `mid`와 `light`도 파일이 있으면 응답에 포함한다.

원본 사진은 일반 모드에서 파일로 저장하지 않고 메모리로 처리한다. 하지만 **생성 베이스 JPG에는 얼굴이 포함된다.** “원본 파일 미보관”이 “얼굴 이미지 데이터 미보관”이라는 뜻은 아니다. 외부 Google AI에도 사용자 이미지가 전송된다.

### 22.3 디버그 모드 예외

`STUDIO_DEBUG=true`면 원본·AI 원본 결과를 `studio_debug/{asset_dir}/`에 PNG로 저장한다. 실패 판정 때도 진단 이미지를 남길 수 있다. static 바깥이라 일반 결과 URL로 바로 노출하지 않지만 자동 정리 대상은 아니다.

따라서 “원본은 절대 저장하지 않는다”는 설명은 디버그 설정까지 포함하면 틀리다. 실제 .env 비밀값이나 사용자 사진 파일은 이 문서에 옮기지 않았다.

### 22.4 결과 정리

`STUDIO_KEEP_DAYS` 기본 7일이 지난 작업 행을 지우고, DB에 없는 결과 폴더도 정리한다. 정리 배치에서 `cleanup_renders()`를 호출한다. 기준은 created_at이며 회원 결과도 이 스튜디오 보관 정책의 대상이다.

계정 탈퇴는 HairRender 행도 삭제한다. 다만 `delete_user()`가 즉시 파일을 지우는 것은 아니고, 스튜디오 정리가 살아 있는 DB 폴더 목록과 비교할 때 고아 폴더를 정리한다.

현재 비회원→회원 이관 함수는 SkinAnalysis·HairRecRun·FaceAnalysis를 옮기며 HairRender는 포함하지 않는다. 회원의 내 분석 이력 목록도 피부·헤어 추천이며 합성 이력까지 제공하지 않는다.

## 23. 인증·사용량·오류·운영 한계

- 생성은 촬영 가능한 actor만 허용한다. 비회원 기본 studio 한도는 하루 2회, 한국 시간 자정 기준이다.
- 사용량은 HairRender 행을 세며 pending/done은 포함하고 failed는 제외한다. 회원·키오스크는 해당 quota 제한을 받지 않는다.
- 상태 조회는 `_own()`으로 회원번호 또는 비회원 세션 일치를 검사한다.
- 현재 run_id는 생성 API에서 존재 여부만 검사하며, 그 추천 실행의 본인 소유 여부까지 검사하는 코드는 없다.
- 상태 조회의 소유권 검사와 `/static/studio/...` 파일 접근은 별개다. static 파일은 URL 자체에 회원 검사 미들웨어가 붙은 구조가 아니다. 무작위 경로는 추측을 어렵게 할 뿐 접근 제어를 대체하지 않는다.
- BackgroundTasks는 서버 프로세스 안에서 실행된다. 영속 작업 큐·실패 재처리·서버 재시작 후 pending 복구가 구현된 것으로 볼 수 없다.
- `_lock`은 MediaPipe 공유 그래프를 보호하지만 여러 AI 작업의 전체 동시 실행 수를 제한하는 큐는 아니다.
- 사진 바이트 길이는 읽은 뒤 검사하므로 네트워크·메모리 차원에서 엄격한 스트리밍 업로드 제한을 구현한 것은 아니다.
- 브라우저 폴링 제한 180초와 외부 HTTP timeout 180초는 전체 파이프라인 시간이 같다는 뜻이 아니다. 전후처리까지 더해질 수 있다.

이는 현재 구현의 범위를 설명한 것이며 이번 문서 작성 과정에서 기능을 수정한 것은 아니다.

## 24. 이전 결과와의 호환

과거에 생성한 결과에는 `mid`나 `light` 이미지와 마스크가 남아 있을 수 있다. API는 완료된 작업의 베이스 파일이 있을 때 해당 URL을 제공한다. 새 작업은 중간 갈색 이미지와 마스크를 저장한다.

## 25. 테스트에서 무엇을 검증하는가

기존 테스트 소스에서 확인한 범위다. 이 학습 문서를 작성하면서 테스트를 새로 실행하거나 유료 생성 품질을 다시 측정하지는 않았다.

- `GeminiImageTest`: 출력 비율 선택·첫 이미지 추출·오류 변환.
- 사진 검사: 기울어진·돌아간·작은 얼굴 거절 및 정면 통과.
- 프롬프트 검사: 참조 역할·여성 컷·컬·남성 long·시스루 지시 충돌 방지.
- 생성 검사: AI를 1회만 호출하고 실패 시 재시도·후처리 진행을 하지 않음.
- 마스크 검사: 입력 패딩 제거, 이마 구간 가닥, 마스크 파일 구성.
- quota 검사: 설정 한도와 실패 작업 제외.
- 통합 테스트: AI 대역을 사용한 생성→조회→소유자 거절과 마이그레이션 유지.
- DOM 테스트: 추천 없이 직접 업로드, run_id 선택 전송, 필터·재시도·빈 카탈로그·폴링·색 패널.

대역 테스트는 API와 조건 분기를 검증하는 증거다. 다양한 피부톤·짧은 남성 머리·곱슬·복잡한 배경·실제 Google 출력의 시각적 자연스러움까지 보장하지 않는다.

## 26. 알려진 시각적 한계

1. 분할 모델이 저해상도여서 비치는 앞머리 사이 피부나 가는 가닥을 정확히 분리하기 어렵다.
2. 머리색과 비슷한 눈썹이 일부 염색되거나 가닥과 함께 처리될 수 있다.
3. 카탈로그 썸네일이 작으면 스타일 세부 형태 전달이 부족하다.
4. 원본에 가려졌던 턱·목·배경은 실제로 관측한 원본 픽셀로 복구할 수 없어 생성 내용에 의존한다.
5. 얼굴 핵심 영역을 보존하려 해도 경계·재인코딩·분할 오차 때문에 완전 동일 얼굴을 보장하지 않는다.
6. 색상은 화면의 시뮬레이션이며 탈색 이력·모발 상태·염료·조명을 반영한 실제 염색 예측이 아니다.
7. 외부 AI 전송·생성 파일 보관·디버그 원본 보관의 차이를 실제 약관과 운영 설정에 반영할 필요가 있다.
