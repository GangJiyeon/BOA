## 이번에 변경한 것

1. 판정 구간 검증: `higher_is_better` 값이 맞더라도 `개선 필요` 구간이 반대쪽에 있으면 거부한다.
   높은 값이 양호한 지표는 0부터, 낮은 값이 양호한 지표는 100까지 이어지는 개선 구간이어야 한다.
   전체 범위를 개선 필요로 설정하거나 지표 코드를 중복 정의한 경우도 거부한다.
   경계 숫자 자체는 기존 DB 설정을 존중하며 33/67을 엔진에 고정하지 않는다.
2. `ranking_tie_count`: 상위 5개뿐 아니라 전체 후보 중 매칭 수·세트 여부가 같은 제품 수를 반환한다.
   자신도 포함한다. 임상 효과가 같다는 뜻이 아니며 ID를 제외한 정렬 조건이 같다는 뜻이다.
3. 화면: 전체 개선 대상 수와 규칙으로 평가 가능한 지표 수를 분리한다.
   예를 들어 개선 대상 5개, 홍조 보류이면 제품은 최대 `4 / 4개 평가 가능 지표에 성분 매칭`으로 표시한다.
   이 표현도 효과가 충분하다거나 100% 적합하다는 뜻은 아니다. 정렬 기준과 동점 규모를 함께 표시한다.
4. 홍조만 개선 대상일 때 활성 매칭 규칙이 없어서 추천을 보류한다고 설명한다.
   제품이 모두 부적합해서 결과가 없는 것과 구분한다.
5. 18개 시나리오 감사 스크립트와 회귀 테스트 12개를 추가했다.

제품 포함/배제 규칙, 점수 가중치, 실제 제품 순서는 바꾸지 않았다.
이미 설치된 규칙의 해시나 내용도 바꾸지 않았다.

## 성분별 태그 운영: 다음 검토 순서

현재 `ingredients`는 성분 사전, `product_ingredients`는 함유 연결이다.
정규화 완료가 효능 태깅 완료를 의미하지 않는다. `category_ingredients`가 성분과
피부 판정 구간 사이의 버전별 규칙이며 근거·한계는 `cosmetic_rule_evidence`에 연결된다.

근거 조사에서 나누어 기록할 항목:

- 정확한 성분 식별자와 DB 이름(별칭은 확인된 것만 연결).
- 일반적인 배합 기능, 사람 대상 연구 결과, 프로젝트 지표 연결 추론을 각각 분리.
- 연구 대상·농도·제형·부위·기간과 실제 제품에서 확인 가능한 항목.
- `match` / `exclude` / `caution`, 적용 조건과 미적용 조건, `active` / `deferred`.
- 읽은 출처 범위(본문/초록/검색 요약), 근거 한계와 변경 이유.

출처 재확인: [AAD rosacea skin care tips](https://www.aad.org/public/diseases/rosacea/triggers/tips),
2026-10-05 본문 열람. 성분 회피 목록 외 제품 종류와 각질 관리 지침도 포함되어 있다.
이를 일반 홍조 점수에 적용하는 것은 별도의 프로젝트 정책 판단이다. 이번 패치에서
해당 지침을 근거로 자동 배제 대상이나 질환 진단을 추가하지 않았다.

활성/보류의 기준이 성분별로 일관적인지도 재검토해야 한다. 예컨대 농도 미확인을 이유로
한 규칙은 보류하면서 다른 규칙은 활성화했다면 그 차이를 근거 수준과 적용 범위로 설명해야 한다.
새 판정이 확정되면 기존 v1을 덮어쓰지 않고 새로운 규칙 버전의 dry-run → 검수 → 적용으로 진행한다.

## 아직 해결하지 않은 것

- 사용자 맞춤 우열의 정답 데이터 없음. Precision@5 같은 정확도 숫자를 만들 수 없음.
- 용량·기획별 동일 제품 식별 및 중복 제거, 완제품 사용법/얼굴 사용 부위 확인.
  제품명에 '바디로션'이 있는 A000000246674도 사용 방식 필터는 통과한다.
  현재 매칭 성분이 없어 최종 추천되지 않지만 향후 규칙 확장 전에 부위 검증이 필요하다.
- 제품별 농도·pH·제형 및 개인 반응 자료 부족.
- 판정 구간 안의 심각도와 순위 관계. 측정값 의미 합의 전 임의의 심각도 가중치를 넣지 않았다.

- 테스트 기대값은 소프트웨어 계약이며 전문가가 라벨링한 제품 적합성 정답이 아니다.

## 재현 및 적용

사용자가 이미 rules-db-v1 패치, 마이그레이션, 시드를 적용한 상태를 기준으로 한다.
이번 문서는 참고용이며 별도로 실행하거나 DB에 넣지 않는다. 아래 패치를 적용하면 코드와 함께 들어간다.

```powershell
cd C:\Users\USER\Desktop\BOA-git
git apply --check "$HOME\Downloads\boa-cosmetic-quality-v1.patch"
# 위 검사에 오류가 없을 때만 다음 실행
git apply "$HOME\Downloads\boa-cosmetic-quality-v1.patch"
cd backend
docker compose exec api python -m unittest discover -s tests -v
```

DB 업그레이드나 시드 명령은 필요하지 않다. 테스트 성공 후 프론트 검증:

```powershell
cd ..\frontend
pnpm build
pnpm lint
```

`node_modules missing`이면 `pnpm install --frozen-lockfile`을 먼저 실행한다.
오류가 나면 무시하고 넘어가거나 lockfile을 갱신하지 말고 출력부터 확인한다.

감사 스크립트는 backend에서 아래처럼 실행한다. 원본 DB 경로는 실제 파일 위치로 지정한다.
컨테이너에 SQLite가 없다면 그 안에서 실행할 수 없다. 원본 파일을 바꾸지는 않는다.

```sh
python scripts/audit_cosmetic_quality.py /path/to/beauty_catalog.db
```

보고서는 stdout JSON으로 출력하며 원본 해시, 규칙 버전/해시, 기본 판정 구간, 성분별 연결 수,
18개 시나리오의 후보·동점 분포, 공유 근거 사용 수와 상위 5개를 포함한다.
5개씩 엔진을 호출하여 전체 후보를 복원하므로 필터 로직의 별도 복제 없이 검수한다.

검증: backend 55개 테스트 통과, frontend TypeScript/Vite 빌드·lint 통과.
이 작업의 실제 브라우저 클릭 검수와 사용자 PC 적용은 아직 하지 않았다.
