# BOA 회원 기능 학습 가이드

작성 기준: 2026-11-15 재검토, 현재 로컬 작업 폴더의 코드. 커밋되지 않은 변경도 포함한다. 최초 정리와 1~3단계 작업 기록은 2026-11-14 기준이다.

> 같은 날 1단계 연동 작업을 반영했다. 피부·헤어 생성은 서버 actor로 소유자를 저장하며, 조회·헤어 추천 재사용·수분 측정 저장은 소유자를 검사한다. 비회원 횟수 제한도 연결했다. 구체적인 변경과 검증은 [1단계 작업 기록](account-integration-step1.md)을 참고한다.

> 2단계에서는 [선택 동의·회원 탈퇴 화면](account-integration-step2.md)을 연결했다. 동의 변경은 서버 성공 응답 후 반영하며, 탈퇴 확인·실패 상태 유지·성공 후 결과 초기화를 구현했다.

> 3단계에서는 [내 분석 이력 조회](account-integration-step3.md)를 연결했다. 로그인한 회원의 피부 분석·헤어 추천을 최신순으로 조회하고 필터·페이지 이동·상세 결과 보기를 제공한다.

> **2026-11-25 변경**: 이메일 코드 로그인과 다국어(언어 선택·저장)를 제거했다. 로그인은 Google만 지원한다. `email_verifications` 테이블과 `users.language` 칼럼은 마이그레이션 `f1210a1b2c3d`로 삭제했다. 아래 본문의 이메일 로그인(4.5, 5장 등)·언어 관련 설명은 제거 전 기록이다.

이 문서는 회원 기능을 **사용자 행동 → API → 서비스 → DB → 응답 → 화면** 순서로 이해하기 위한 설명이다. 실행 중인 운영 서버를 검증한 문서는 아니다.

- **[결정 기록]**: 작성자가 기존 문서에 명시한 구현 이유.
- **[코드 확인]**: 현재 소스에서 직접 확인한 동작.
- **[해설/추론]**: 동작을 이해하기 위한 설명 또는 코드에서 추론한 의미. 작성자의 확정된 의도와 구분한다.

## 1. 먼저 이해할 전체 구조

BOA는 비밀번호를 저장해서 로그인하는 서비스가 아니다. 이메일로 받은 6자리 코드를 확인하거나 Google 계정을 인증한 뒤 로그인한다. 처음 인증한 이메일이면 바로 회원을 만들지 않고, 임시 가입 토큰을 발급한다. 사용자가 추가 정보와 약관 동의를 제출해야 가입이 완료된다.

```text
이메일 코드 인증 ─┐
                 ├─ 기존 회원 → 로그인 → 인증 쿠키 발급
Google 인증 ─────┘
                 └─ 신규 사용자 → 가입 토큰
                                  ↓
                         가입 정보 + 현재 약관 동의
                                  ↓
                   회원 생성 + 동의 이력 + 비회원 결과 이관
                                  ↓
                              자동 로그인
```

로그인 후에는 짧은 수명의 액세스 토큰으로 요청을 인증하고, 만료되면 긴 수명의 리프레시 토큰으로 토큰을 다시 받는다. 프론트는 인증 쿠키를 직접 읽지 않고 서버에 현재 요청자 종류를 물어본다.

### 현재 기능과 보류한 항목 — 2026-11-15 문서 정리

- 이메일 인증과 언어 저장은 2026-11-25에 코드·API·화면·DB에서 제거했다.
- PHOTO_STORAGE 동의 이력은 변경할 수 있지만 철회 시 파일 삭제는 TODO다. 스튜디오 생성 이미지·디버그 원본의 보관과 함께 판단해야 한다.
- QR 조회·이관 API는 백엔드에 유지한다. 쓰지 않던 프론트 getQrResults·claimQrResults·resultToken은 2026-11-25에 삭제했다. QR 화면을 만들 때 다시 추가한다.
- UserHairPreferences 모델·테이블은 존재하지만 현재 앱에서 선호도를 읽고 쓰는 경로는 확인되지 않았다. 요청별 선호 조건은 HairRecRun에 저장한다. 이번 정리에서 테이블·기존 마이그레이션을 삭제하지 않았다.
- 호환용 user_id·guest_id 입력 필드는 일부 스키마에 남아 있어도 저장 소유자는 서버 actor를 사용한다. 입력 제거는 별도 API 계약 변경이다.
- 토큰 탈취 시 세션 전체 차단·리프레시 재사용 탐지는 캡스톤 범위의 알려진 한계로 남기기로 했다. 구현 완료를 뜻하지 않는다.

## 3. 계층을 나눈 이유와 요청 처리 방식

### 3.1 라우트: HTTP 세계와 연결

`api/routes/auth.py`의 함수는 요청을 받고, 서비스를 호출하고, 오류를 HTTP 상태 코드로 바꾸고, 성공하면 커밋한다. 예를 들어 재발송 제한이라는 서비스 예외를 `429`로 바꾼다.

### 3.2 서비스: 실제 업무 규칙

`services/email_auth.py`는 인증 코드의 유효시간·시도 횟수를 처리한다. `services/signup.py`는 약관 검증과 회원 생성에 집중한다. 프론트 화면을 어떻게 그리는지는 알지 못한다.

[해설/추론] 이런 분리 덕분에 이메일·Google·개발용 로그인에서 공통 `auth.login()`을 재사용할 수 있다. 같은 규칙을 여러 API에 복사하면 수정할 때 일부만 바뀔 위험이 생긴다.

### 3.3 스키마와 모델의 차이

- **스키마(Pydantic)**: HTTP로 어떤 값이 들어오고 나가는가. 잘못된 언어 값, 6자리가 아닌 코드 등을 거른다.
- **모델(SQLAlchemy)**: DB에 어떤 칼럼과 제약이 있는가. 이메일 중복 같은 최종 데이터 무결성을 지킨다.
- **서비스 검사**: 현재 약관인지, 이미 연결된 Google 계정인지처럼 DB 상태에 따라 달라지는 규칙을 검사한다.

셋은 서로 대체 관계가 아니다. 예를 들어 이메일 형식 검증을 통과해도 기존 회원과 같은 이메일이면 DB의 UNIQUE 제약에 걸릴 수 있다.

### 3.4 Depends와 요청자 정보

`Depends(get_db)`는 요청 처리에 사용할 DB 세션을 전달한다. `Depends(get_actor)`는 쿠키를 해석해 요청자 정보를 전달한다. `Depends(require_user)`는 회원만 허용한다.

[해설] 화면에서 버튼을 숨기는 것과 서버 접근 제한은 다르다. 사용자는 브라우저 개발 도구나 별도 HTTP 클라이언트로 API를 직접 호출할 수 있으므로 서버가 다시 검사해야 한다.

## 4. DB 구조: 왜 테이블이 여러 개인가

### 4.1 users — 회원의 현재 기본 정보

| 필드 | 의미·설계 |
|---|---|
| id | 내부 회원 번호, 토큰과 결과 소유자 식별에 사용 |
| email | 소문자로 정규화, UNIQUE |
| google_sub | Google 계정 고유 식별자, nullable·UNIQUE |
| language | ko/en/zh/ja. 허용 값은 API 스키마에서 제한 |
| nationality | 두 글자 국가 코드. 모델에서는 nullable지만 일반 가입 요청에서는 필수 |
| resides_in_korea | 한국 거주 여부. 모델 nullable, 일반 가입 요청 필수 |
| created_at | 생성 시각 |
| last_login_at | 로그인 성공 시 갱신 |

비밀번호 칼럼은 없다. 이메일 인증과 Google 인증으로 본인 확인을 처리하기 때문이다.

[결정 기록] 테이블명·기본키·Alembic 사용 방식은 기존 피부 모듈과 통일했다. 계정 모듈만 별도 규칙을 도입하면 팀 통합이 어려워지기 때문이다.

이메일 소문자화는 이 서비스의 계정 식별 정책이다. 모든 이메일 공급자의 세부 규칙까지 구현한 이메일 정규화는 아니다. Gmail의 점이나 `+태그`를 제거하는 코드도 없다.

### 4.2 terms — 약관의 버전 정보

`type`, `version`, `required`, `effective_at`을 저장한다. `(type, version)`은 유일하다. 본문 자체는 이 테이블에 없다.

현재 약관은 `effective_at <= 현재 시각`인 행 중 종류별 시행일이 가장 최신인 행이다. 버전 문자열을 사전순으로 비교하는 것이 아니다. `current_terms()`는 종류별 DISTINCT와 정렬을 사용하므로 PostgreSQL의 DISTINCT ON 동작을 이해하면 좋다.

[결정 기록] DB에는 동의 대상의 종류·버전·필수 여부를 두고, 본문은 프론트에서 관리하기로 했다. 다만 **현재 본문 연결이 완료됐다는 의미는 아니다.**

### 4.3 consent_histories — 현재 값이 아닌 변경 이력

`user_id`, `terms_id`, `action(AGREE/WITHDRAW)`, `created_at`을 저장한다. 기존 행을 수정하는 대신 새 행을 추가한다.

```text
PHOTO_STORAGE v1 AGREE
PHOTO_STORAGE v1 WITHDRAW
PHOTO_STORAGE v2 AGREE
→ 해당 종류의 가장 최근 기록이 현재 상태
```

[결정 기록] 어떤 버전에 동의·철회했는지 남기려는 구조다. 단순히 `users.marketing = true`만 두면 과거 상태와 동의한 버전을 알기 어렵다.

### 4.4 refresh_tokens — 장기 로그인 자격

회원별로 여러 행이 존재할 수 있다. 원문 대신 SHA-256 해시를 저장하고 만료 시각을 둔다. `user_id` 외래키는 회원 삭제 시 CASCADE다.

[해설] 로그인 기기마다 토큰을 따로 발급할 수 있는 형태다. 현재 로그아웃은 해당 요청의 리프레시 토큰만 삭제하며 모든 기기의 토큰을 삭제하지 않는다.

### 4.5 email_verifications — 진행 중인 이메일 인증

이메일 자체가 기본키다. 이메일당 한 행이므로 재발급하면 이전 코드를 덮어쓴다. `code_hash`, `attempt_count`, `sent_at`, `expires_at`을 저장한다. 인증 성공 시 행을 삭제한다.

[결정 기록] `attempt_count`는 SQL로 직접 넣을 때도 기본값이 생기도록 `server_default=0`을 둔다. Python ORM 기본값과 DB 기본값의 차이를 공부할 수 있는 예다.

### 4.6 guest_sessions와 kiosks

비회원 세션은 UUID로 식별하며 회원으로 전환되면 `user_id`를 채운다. QR 토큰 해시, 세션 만료 시각, 동의한 얼굴 이미지 약관 ID도 저장한다. 키오스크 기기와 그 기기를 사용하는 사람의 세션은 별개다.

회원과 연결된 동의 이력·리프레시 토큰·비회원 세션은 회원 삭제 시 CASCADE로 삭제된다. 반면 분석 결과는 계정 코드가 직접 삭제하는 부분이 있으므로 “회원 삭제 한 줄이면 모든 데이터가 자동 삭제된다”고 이해하면 안 된다.

## 5. 이메일 로그인: 함수 단위로 따라가기

### 5.1 인증 코드 요청

사용자가 이메일을 입력하면 `AccountPage.send()` → `sendCode()` → `POST /api/auth/email/send`로 요청한다.

1. `EmailSendRequest`가 이메일 형태와 길이(최대 255)를 검사한다.
2. `normalize_email()`이 앞뒤 공백 제거와 소문자화를 수행한다. 단, 스키마 검증이 먼저이므로 API에 공백이 있는 이메일을 직접 보내면 정규화 전에 거절될 수 있다. 프론트는 `trim()`해 보낸다.
3. `email_auth.issue_code()`가 기존 행을 조회한다.
4. 마지막 발송 이후 60초가 지나지 않았으면 `ResendTooSoon` → HTTP 429.
5. `secrets.randbelow(1_000_000)`으로 숫자를 만들고 6자리로 채운다. `000123`도 가능하므로 문자열로 다룬다.
6. 이메일과 코드를 묶어 HMAC을 계산하고 DB에 저장한다.
7. `attempt_count=0`, `sent_at=현재`, `expires_at=현재+10분`으로 설정한다.
8. 라우트가 커밋한 뒤 `mail.send_login_code()`를 호출한다.
9. `{resend_seconds: 60, dev_code: null}`을 반환한다. 개발 로그인 설정이 켜졌을 때만 원문 코드가 응답에 포함된다.

**왜 가입 여부를 알려주지 않는가?** [결정 기록] 코드 발송 단계에서 “없는 회원입니다”라고 하면 타인의 이메일 가입 여부를 알아낼 수 있다. 그래서 기존·신규 모두 같은 형태로 응답한다. 인증 성공 후의 가입 분기는 이메일 소유를 확인한 다음이다.

**왜 발송 전에 커밋하는가?** [코드 확인] 실제 호출 순서가 그렇다. [해설/추론] 메일을 받은 직후 검증할 코드가 DB에 있어야 한다는 의미가 있지만, 향후 SMTP 연결 후 발송이 실패하면 DB에는 코드와 재발송 제한이 남을 수 있다. 현재는 DB와 외부 발송을 하나의 원자적 작업으로 보장하지 않는다.

### 5.2 코드를 일반 SHA-256이 아닌 HMAC으로 저장하는 이유

6자리 숫자는 경우의 수가 100만 개뿐이다. DB에 단순 해시만 있으면 모든 후보를 계산해 비교하기 쉽다.

```text
HMAC-SHA256(JWT_SECRET, "정규화된이메일:6자리코드")
```

[결정 기록] 서버 비밀키가 있어야 후보 해시를 만들 수 있도록 HMAC을 사용한다. 이메일도 입력에 넣어 다른 이메일의 코드 해시와 구분한다. 원문 코드·비밀키가 함께 유출되는 상황까지 해결하는 것은 아니다.

검증에는 `hmac.compare_digest()`를 사용한다. [해설] 단순 문자열 비교보다 비교 시간 차이를 통한 정보 노출을 줄이기 위한 함수다.

### 5.3 인증 코드 검증

`AccountPage.verify()` → `verifyCode(sentEmail, code)` → `POST /api/auth/email/verify`.

`sentEmail`을 별도 보관하므로 화면에 입력 중인 이메일이 아니라 실제 코드 요청에 사용한 이메일을 검증한다. 이메일을 바꾸면 기존 코드·가입 토큰 상태를 초기화한다.

서버 처리 순서는 다음과 같다.

1. 이메일당 인증 행을 조회한다.
2. 행이 없거나 만료 → 400, 다시 받으라는 메시지.
3. 시도 횟수가 이미 5회 이상 → 정답을 보내도 400.
4. 코드 불일치 → 횟수 1 증가, 400.
5. 일치 → 인증 행 삭제.
6. 회원 존재 여부로 기존 로그인과 신규 가입을 분기한다.

중요한 구현은 실패 때도 `db.commit()`한다는 점이다. `verify_code()`는 실패 시 예외 대신 메시지를 반환한다. 라우트는 그 메시지를 받으면 횟수 변경을 커밋한 뒤 HTTP 오류를 발생시킨다.

[결정 기록] 잘못된 코드의 횟수도 저장해야 하기 때문이다. 횟수를 올린 후 트랜잭션을 롤백하면 공격자가 계속 시도할 수 있다.

다섯 번째 오답은 “코드가 올바르지 않다”이고, 그다음 요청부터 횟수 초과 검사에 걸린다. 재발송하면 횟수가 0으로 돌아가며 이전 코드는 무효다. 성공하면 행을 삭제하므로 같은 코드를 다시 검증할 수 없다.

### 5.4 기존 회원과 신규 사용자의 분기

기존 회원이면 `auth.login()`으로 쿠키를 발급하고 마지막 로그인 시각을 갱신한다. 응답은 `signup_required=false`와 저장된 언어다.

신규이면 회원을 생성하지 않고 `signup_required=true`, `signup_token`을 반환한다. 이 JWT는 “해당 이메일의 인증을 마쳤다”는 임시 증명이다.

## 6. 가입 토큰과 회원가입

### 6.1 가입 토큰은 로그인 토큰과 다르다

가입 토큰은 10분 유효하고 `sub=이메일`, `type=signup`이다. Google 인증이면 `google_sub`도 포함한다. 액세스 토큰은 `sub=회원번호`, `type=access`다.

[결정 기록] 같은 JWT 형식을 사용하더라도 `type`을 검사해 가입 토큰을 로그인 자격으로 쓰지 못하게 한다. 프론트는 가입 토큰을 React 메모리 상태에 보관하고 가입 요청 본문으로 전달한다.

[해설] JWT는 서명된 데이터이지 암호화된 데이터가 아니다. 내용을 숨기는 용도가 아니라, 서버가 발급한 내용이 변조되지 않았는지 확인하는 용도다. 가입 토큰을 한 번 사용했다는 별도 DB 기록은 없고, 중복 회원 생성은 UNIQUE 제약 등으로 방어한다.

### 6.2 가입 요청 필드

```json
{
  "signup_token": "인증 성공 응답에서 받은 JWT",
  "language": "ko",
  "nationality": "KR",
  "resides_in_korea": true,
  "agreed_terms_ids": [1, 2, 3, 4]
}
```

숫자는 예시다. 약관 ID를 고정해서 사용하면 안 되고 `/api/terms/current` 응답의 실제 ID를 사용해야 한다.

- `language`: ko/en/zh/ja 중 하나.
- `nationality`: 대문자 영문 두 글자. 실제 존재하는 국가 코드 목록과 대조하는 검사는 없다.
- `resides_in_korea`: boolean.
- `agreed_terms_ids`: 체크한 현재 약관 ID 목록.
- 이메일·Google 식별자는 사용자가 별도로 보내는 값을 신뢰하지 않고 검증된 가입 토큰에서 가져온다.

### 6.3 서버 가입 순서와 트랜잭션

`POST /api/auth/signup`은 다음을 수행한다.

1. 이미 회원으로 로그인한 요청이면 400.
2. 가입 토큰의 서명·만료·종류 검사. 실패하면 401.
3. 이메일이 이미 가입돼 있으면 409.
4. 제출한 약관이 현재 약관인지, 필수가 빠지지 않았는지 검사.
5. `signup.create_user()`로 회원 생성.
6. `db.flush()`로 INSERT를 DB에 전달해 회원 ID 확보 및 중복 제약 확인.
7. 체크한 약관마다 `ConsentHistory(action=AGREE)` 추가.
8. 현재 유효한 비회원 세션이 있으면 결과를 회원에게 이관.
9. `auth.login()`으로 로그인 토큰 생성 및 응답 쿠키 설정.
10. 한 번의 `db.commit()`으로 DB 변경 확정.
11. 이관한 경우 비회원 쿠키 삭제, 201 응답.

[결정 기록] 회원 생성·동의 기록·이관·로그인을 한 트랜잭션으로 처리해 일부만 저장된 회원이 남지 않게 한다.

**flush와 commit의 차이:** flush는 SQL을 보내 ID와 제약 검사 결과를 얻지만 트랜잭션을 확정하지 않는다. commit은 변경을 최종 확정한다. 여기서 flush를 commit으로 바꾸면 뒤쪽 이관이 실패해도 회원만 남는 상황이 생길 수 있다.

쿠키는 DB 행이 아니므로 DB 트랜잭션이 쿠키까지 원자적으로 저장하는 것은 아니다. 쿠키는 응답에 실려 클라이언트에 전달된다. 또한 “실패하면 항상 보상 작업이 실행된다”는 별도의 분산 트랜잭션 구현도 없다.

### 6.4 중복 검사 두 번의 이유

이메일을 미리 조회하더라도 두 요청이 동시에 오면 둘 다 “없음”을 볼 수 있다. 그래서 DB의 `UNIQUE(email)`과 `UNIQUE(google_sub)`가 최종 방어다.

[결정 기록] 회원 생성의 `IntegrityError`를 잡고 롤백한 후 409로 바꾼다. 친절한 사전 검사와 DB 무결성 검사를 함께 둔 것이다. 현재 try 블록은 `create_user()` 호출을 감싸므로 모든 종류의 후속 DB 오류가 동일한 409로 변환되는 것은 아니다.

## 7. 약관 검증과 동의 상태

### 7.1 기본 약관 6종

| 종류 | 필수 여부 | 의미 |
|---|---|---|
| SERVICE | 필수 | 서비스 이용 |
| PRIVACY | 필수 | 개인정보 수집·이용 |
| AGE_14 | 필수 | 만 14세 이상 확인 |
| FACE_IMAGE | 필수 | 얼굴 이미지 처리 |
| PHOTO_STORAGE | 선택 | 사진 보관 |
| MARKETING | 선택 | 마케팅 수신 |

[결정 기록] 회원은 가입할 때 FACE_IMAGE에 동의하므로 회원용 촬영 전 동의 API를 별도로 만들지 않기로 했다. AGE_14는 사용자 확인을 받는 구조이며 신분증 등으로 실제 나이를 검증하는 구현은 아니다.

### 7.2 왜 약관 이름이 아닌 ID를 보내는가

`FACE_IMAGE에 동의했다`만으로는 어떤 버전에 동의했는지 알 수 없다. 서버는 현재 약관의 ID 집합과 제출 ID를 비교한다.

- 없는 ID 또는 과거 버전 ID → 400, 약관 갱신 안내.
- 필수 누락 → 400, 빠진 약관 종류 안내.
- 중복 ID → set으로 정리해 동의 기록 중복 생성을 피한다.

[해설] 가입 화면을 켜 둔 사이 약관이 바뀌는 경우도 서버에서 거절할 수 있다. 프론트 체크박스 검증만으로는 해결할 수 없는 문제다.

### 7.3 현재 동의 상태 계산

`consent_statuses()`는 이력을 `created_at DESC, id DESC`로 조회하고 종류별 첫 기록을 사용한다. 시각이 같아도 ID로 순서를 보완한다. 기록이 없으면 `agreed=false`, `version=null`이다.

주의: 현재 약관 버전에 동의했는지 비교해서 상태를 취소하는 코드는 없다. 예전 버전에 AGREE가 있으면 현재 목록에서도 `agreed=true`이고 `version`에는 그 예전 버전이 표시될 수 있다. 자동 재동의 요구 기능으로 이해하면 안 된다.

### 7.4 선택 약관 변경

`POST /api/me/consents`에 `{type, action}`을 보낸다. action은 AGREE 또는 WITHDRAW다.

현재 약관이 없으면 400, 필수 약관이면 400이다. 현재 상태와 요청 상태가 같으면 행을 추가하지 않는다. 변경 시 현재 약관 ID로 이력을 추가한 뒤 상태를 다시 계산한다.

[결정 기록] 의미 없는 중복 이력을 줄이고, 필수 동의를 유지할 수 없다면 탈퇴를 안내하기 위한 정책이다. PHOTO_STORAGE 철회 시 실제 사진 삭제는 서비스 코드에 TODO로 남아 있다.

## 8. Google 로그인과 이메일 계정 연결

### 8.1 브라우저에서 백엔드까지

`GoogleLoginButton.tsx`는 `@react-oauth/google`을 사용한다. `flow='auth-code'`로 팝업을 열고 Google에서 받은 인가 코드를 `POST /api/auth/google`로 전달한다. 백엔드는 기본 `redirect_uri=postmessage`로 코드를 교환한다.

프론트의 `VITE_GOOGLE_CLIENT_ID`가 없으면 버튼을 비활성화한다. 백엔드의 client ID 또는 secret이 없으면 503이다. 클라이언트 ID는 프론트에도 필요하지만 **client secret은 백엔드 설정**이다.

### 8.2 인가 코드와 ID 토큰의 차이

인가 코드는 Google 서버에서 인증 정보를 교환하기 위한 일시적 값이다. 백엔드는 code·client ID·secret·redirect URI를 Google token endpoint로 보내 `id_token`을 받는다. HTTP 통신 제한 시간은 10초다.

ID 토큰은 Google이 인증한 사용자의 정보가 담긴 JWT다. 단순히 내용을 읽고 믿는 것이 아니라 아래를 검증한다.

1. Google 공개키로 서명 확인. `PyJWKClient`가 공개키를 조회·캐시하고 키 변경에 대응한다.
2. 알고리즘은 RS256으로 제한.
3. 발급자 issuer가 Google인지 확인.
4. audience가 이 서비스의 Google client ID인지 확인.
5. 토큰 만료 검증.
6. email 존재 및 `email_verified is True` 확인.

[결정 기록] 다른 앱용 토큰이나 미인증 이메일로 타인의 기존 이메일 계정을 연결하는 일을 방지하려는 선택이다.

### 8.3 회원 찾기와 자동 연결

`find_or_link_google_user()` 순서:

1. `google_sub`가 같은 회원 조회 → 있으면 그 회원 로그인.
2. 없으면 인증된 이메일로 회원 조회.
3. 같은 이메일 회원의 `google_sub`가 비어 있으면 연결 후 로그인.
4. 다른 Google 식별자가 이미 연결돼 있으면 409.
5. 둘 다 없으면 Google 식별자를 포함한 가입 토큰 발급.

[결정 기록] Google 계정 고유값인 sub를 우선하고, 기존 이메일 가입자는 같은 이메일의 Google 로그인으로 이어서 사용할 수 있게 했다. 인증 완료 후에는 이메일·Google 모두 같은 가입 API와 `auth.login()`을 재사용한다.

현재 제공 코드는 Google 계정 연결 해제나 이메일 주소 변경 API를 구현하지 않는다. Google 로그인으로 sub가 일치했다고 기존 DB 이메일을 자동 갱신하는 코드도 없다.

## 9. 로그인 토큰: 짧은 JWT와 긴 무작위 토큰

| 구분 | 액세스 | 리프레시 | 가입 |
|---|---|---|---|
| 형태 | HS256 JWT | 긴 무작위 문자열 | HS256 JWT |
| 기본 수명 | 15분 | 30일 | 10분 |
| 용도 | 일반 API 회원 인증 | 로그인 연장 | 인증된 신규 사용자의 가입 허용 |
| 저장/전달 | HttpOnly 쿠키 | HttpOnly 쿠키, DB에는 해시 | 응답 본문 → 프론트 메모리 → 가입 본문 |
| 서버 검사 | 서명·만료·type | 해시로 DB 조회·만료 | 서명·만료·type |

[과거 결정 기록] 최초 설계는 액세스 JWT를 DB 조회 없이 검사해 비용을 줄이고 유효시간을 짧게 두는 구조였다. 현재 get_actor는 탈퇴 회원 차단을 위해 DB 회원 존재도 확인한다. 포트폴리오에서 설명 가능한 표준적인 토큰 구조를 선택했으며 단순 서버 세션 방식도 검토했다고 기록돼 있다. “JWT가 언제나 더 우수하다”는 결론은 아니다.

`auth.login()`은 `last_login_at`을 바꾸고 `issue_tokens()`를 부른다. 갱신은 `issue_tokens()`를 직접 호출하므로 `last_login_at`을 갱신하지 않는다.

리프레시 토큰은 `secrets.token_urlsafe(32)`로 만든다. DB에는 SHA-256 해시만 저장한다. [결정 기록] 6자리 코드와 달리 충분히 긴 무작위 값이라 단순 해시로 저장·조회할 수 있다는 판단이다. DB 해시가 유출돼도 그 해시 문자열을 원문 토큰처럼 바로 보내는 방식으로는 통과하지 않는다.

## 10. 쿠키 설계에서 가장 중요한 부분

### 10.1 HttpOnly·SameSite·Secure·Path

- `HttpOnly=true`: 프론트 JS에서 인증 쿠키를 직접 읽지 못한다. 대신 브라우저가 요청에 자동으로 붙인다.
- `SameSite=Lax`: 다른 사이트에서 온 요청에 쿠키를 보내는 범위를 제한한다.
- `Secure=COOKIE_SECURE`: HTTPS에서만 쿠키를 보내도록 하는 옵션. 로컬 HTTP 개발에서는 기본 false다.
- 액세스 경로 `/`: 일반 API에 전송.
- 리프레시 경로 `/api/auth`: 그 하위 인증 요청에만 전송.

“갱신·로그아웃에만 전송”이라는 주석은 의도 설명이다. 브라우저의 실제 Path 규칙상 `/api/auth/email/send` 등 같은 경로 아래의 다른 요청에도 전송될 수 있다.

[해설] HttpOnly가 XSS 전체를 막는 것도, SameSite 하나가 모든 요청 위조를 막는 것도 아니다. 현재 계정 코드에서 별도의 CSRF 토큰 검사는 확인되지 않는다. 여기서는 실제 적용된 쿠키 속성과 그 범위를 구분해서 이해하면 된다.

### 10.2 액세스 JWT는 15분인데 쿠키는 왜 30일 남기는가

이 프로젝트의 핵심 결정이다.

```text
JWT 만료 + 쿠키도 없음 → 서버는 익명/비회원이라고 판단할 수 있음
JWT 만료 + 쿠키는 남음 → 서버가 만료를 확인하고 401 반환
                       → 프론트가 refresh 후 원래 요청 재시도
```

[결정 기록] 만료된 회원을 비회원으로 취급하면 회원이 만든 결과가 비회원 쪽으로 저장될 수 있다. 그래서 **쿠키가 보관되는 기간**과 **쿠키 안 토큰의 유효기간**을 의도적으로 다르게 했다.

쿠키가 남았다는 사실은 로그인 자격이 유효하다는 뜻이 아니다. 서버는 매번 JWT 만료를 검사한다. 쿠키 expires는 DB 시간대와 관계없이 UTC로 변환한다. 결정 기록에는 +09 시각을 그대로 넣어 500이 발생한 문제를 고친 흔적이 있다.

### 10.3 동일 출처 API 경로

프론트는 `/api` 상대 경로와 `credentials='same-origin'`을 사용한다. 로컬 Vite proxy와 배포 rewrite로 브라우저 기준 동일 출처에서 API를 부르는 구상이다. 백엔드 main은 허용 origin 목록과 `allow_credentials=True`를 설정한다.

[해설] 백엔드 주소를 다른 출처로 직접 바꾸면 CORS와 쿠키 전송 조건을 함께 검토해야 한다. 상대 경로를 사용하는 현재 구조의 전제를 이해하는 것이 중요하다.

## 11. 요청자 판별: get_actor()

반환하는 `Actor`는 frozen dataclass로 `kind`, `user_id`, `guest_id`, `kiosk_id`를 가진다. 판별 우선순위는 다음과 같다.

1. 유효한 키오스크 토큰 → kiosk.
2. 액세스 쿠키 존재 → JWT가 유효하면 member, 만료·위조면 401.
3. 유효한 비회원 세션 → guest.
4. 나머지 → anonymous.

[결정 기록] 공용 기기의 키오스크 모드를 남은 회원 쿠키보다 우선한다. 키오스크의 guest 세션도 해당 기기에서 시작한 세션만 인정한다. 해제·위조된 키오스크 토큰은 다음 판별로 넘어가지만, 액세스 토큰이 만료됐을 때는 비회원으로 넘기지 않는다.

- `require_user()`: kind가 member인지 검사. 다른 종류는 401.
- `require_analysis_actor()`: 익명 또는 사용자 세션 없는 키오스크면 403.
- `/api/actor`: 프론트에는 kind만 제공. 프론트가 HttpOnly 쿠키를 읽을 수 없기 때문에 필요하다.

현재 member 판별은 JWT 검증 후 DB에서 User 존재도 확인한다. 탈퇴한 회원의 남은 JWT는 401로 거절한다. 마이페이지의 `_get_user()` 검사도 유지한다.

## 12. 토큰 갱신과 프론트 자동 재시도

### 12.1 백엔드 회전 처리

`POST /api/auth/refresh`는 현재 리프레시 쿠키를 해시로 조회한다.

- 없음 → 실패.
- 만료 → 해당 행 삭제 후 실패.
- 유효 → 기존 행 삭제 + 새 액세스·리프레시 토큰 발급.

실패해도 삭제 작업 반영을 위해 커밋한다. 실패 응답은 401이며 인증 쿠키를 지운다. 성공은 204다.

[결정 기록] 갱신마다 리프레시 토큰을 교체해 이전 토큰을 계속 사용할 수 없게 한다. 이전 토큰 재사용을 감지해 모든 기기를 로그아웃시키는 토큰 가족 추적은 구현 범위에 넣지 않았다.

새 리프레시 토큰 만료는 발급 시각 +30일이다. [코드 확인] 최초 로그인 후 무조건 30일에 종료되는 절대 만료가 아니라 갱신 때마다 새 만료가 부여되는 형태다.

### 12.2 프론트 api() 처리 순서

```text
원래 요청 → 401인가?
  아니오 → 성공 처리 또는 오류 표시
  예 → /auth/ 경로인가?
        예 → 인증 자체의 오류로 처리
        아니오 → refresh 1회 → 성공 시 원래 요청 1회 재시도
```

`/auth/signup`의 토큰 만료 같은 오류까지 자동 갱신하면 문제 원인이 다른데 불필요한 갱신을 하게 된다. 그래서 `/auth/`는 제외한다.

재시도 후에도 401이면 오류를 반환한다. 무한 재시도 루프를 만들지 않는다. 204는 JSON을 파싱하지 않고 undefined를 반환한다. 로그아웃·갱신의 빈 응답을 JSON으로 읽으면 오류가 나기 때문이다.

### 12.3 동시에 여러 요청이 401이면

`refreshPromise`를 공유해 같은 페이지에서 갱신 요청을 하나로 합친다. `refreshVersion`은 늦게 도착한 401도 이미 완료된 갱신 결과를 사용하게 한다. `refreshError`는 기존 갱신 실패를 공유한다.

예: `/me`와 `/guest/quota`가 동시에 만료를 발견해도 둘이 같은 refresh를 기다린 뒤 각각 재요청한다. 개별 요청의 AbortSignal은 갱신에 공유하지 않는다. 한 화면 요청 취소가 다른 요청의 로그인 갱신까지 취소하지 않게 하려는 주석이 있다.

**범위에 주의:** 이 변수는 한 JS 실행 환경의 모듈 변수다. 별도 브라우저 탭끼리의 전역 잠금이 아니다. 기존 문서의 “두 탭 동시 갱신” 문제를 완전히 해결했다고 볼 수 없다. 서버 회전 코드에도 명시적 행 잠금은 없으므로 동시 갱신의 원자성을 강하게 보장하는 구현으로 설명하면 안 된다.

### 12.4 갱신 실패 후 UI

갱신 응답이 401이면 `boa:session-expired` 이벤트를 보낸다. `HomePage`는 진행 중인 상태 조회를 취소하고 actor·quota·메모리 결과를 초기화한 뒤 시작 화면으로 보낸다.

503 같은 일시적 서버 오류는 같은 만료 이벤트를 보내지 않는다. 네트워크 장애를 곧바로 로그인 만료로 취급하지 않는 동작이다.

## 13. 프론트 계정 화면에서 배울 점

계정 화면의 첫 페이지는 이메일·국적·분석 이동·로그아웃을 한 행에, 언어 선택·저장을 다음 행에 묶는다. 약관·탈퇴는 `#/start?view=settings`의 별도 설정 화면으로 분리했다. 선택 동의는 설정에서 바로 변경하고, 필수 약관 이력은 펼쳐 볼 수 있다. 설정 주소로 직접 접속하거나 브라우저 뒤로 가기를 사용해도 URL에 따라 화면이 전환된다.


### 13.1 상태 변수의 의미

| 상태 | 용도 |
|---|---|
| email | 현재 입력 중인 이메일 |
| sentEmail | 인증 코드 요청을 완료한 이메일 |
| code | 입력 중인 6자리 코드 |
| signupToken | 인증은 끝났지만 가입 전인 상태의 임시 증명 |
| resendUntil, now | 재발송 카운트다운 |
| language, nationality, resides | 가입 정보 및 언어 설정 |
| agreed | 체크한 약관 ID 목록 |
| member | 서버에서 읽은 회원 정보 |
| task.busy, task.error | 중복 제출 방지·오류 표시 |

### 13.2 입력 변경·요청 취소·중복 제출

`useTask()`는 AbortController를 관리한다. 실행 중 같은 작업의 중복 제출을 막고, 언마운트나 reset 때 요청을 취소한다. 이메일 변경 시 기존 인증 상태를 지우므로 예전 이메일의 가입 토큰을 현재 입력과 혼동하지 않는다.

[해설] HTTP 요청 취소가 이미 서버에서 실행된 DB 변경을 되돌린다는 뜻은 아니다. 화면의 오래된 응답 반영을 막는 기능과 서버 트랜잭션은 별개다.

### 13.3 재발송 제한과 약관 버튼

화면의 초 단위 타이머는 재발송 버튼을 비활성화한다. 서버도 별도로 60초를 검사한다. 화면의 제한만으로는 직접 API 호출을 막을 수 없기 때문이다.

가입 버튼은 SERVICE·PRIVACY·AGE_14·FACE_IMAGE가 모두 체크돼야 활성화된다. 현재 프론트는 네 종류를 명시적으로 검사하지만 서버는 현재 약관의 `required` 값을 기준으로 판단한다. 향후 필수 약관 구성이 바뀌면 두 기준이 달라질 수 있다.

### 13.4 로그인 시 결과 초기화

상위 `HomePage`가 로그인·가입·로그아웃 콜백에 `clearSession()`을 연결한다. 피부·헤어·화장품 최근 결과와 화면 세션 버전을 초기화한다. 로그인 실패 시 성공 콜백이 없으므로 기존 결과를 유지한다.

[결정/프론트 문서] 유효한 비회원의 “세션 이어서 시작”은 사진·입력·결과를 유지한다. 반면 새 사용자로 전환되면 초기화한다. 이는 프론트 메모리 상태 관리이며 서버 DB 결과 삭제와는 다르다.

### 13.5 저장된 언어와 실제 번역은 다르다

로그인 응답에 language가 있고 회원 화면도 값을 읽어 저장한다. 하지만 기존 명세의 `lang` 쿠키·전체 번역 적용 흐름이 현재 계정 코드에 모두 연결된 것은 아니다. `PATCH /me` 성공은 회원 설정 저장의 성공을 뜻한다. 화면 문구 전체가 즉시 번역됐다는 뜻은 아니다.

## 14. 비회원 결과 이관: 계정 기능과 분석 기능의 접점

### 14.1 비회원 시작

비회원은 현재 FACE_IMAGE 약관 ID와 `age_confirmed=true`를 보내 세션을 만든다. 기본 수명은 7일이다. IP는 원문 대신 HMAC으로 저장한다.

[결정 기록] 같은 IP를 묶어 비교하면 되므로 원문 IP 저장을 줄였다. UUID guest_id는 쿠키와 분석 결과 연결에 사용한다.

기존 유효 세션을 서버에서 재사용할 때 QR 토큰은 새로 만들지만 만료 시각은 연장하지 않는다. DB에는 해시만 있어 예전 원문을 재발급할 수 없고, 매번 연장하면 7일 제한 의미가 사라지기 때문이다.

현재 계정 화면은 비회원 이어가기 전에 actor를 다시 확인한다. 이미 guest면 세션 생성 API를 다시 호출하지 않아 기존 이용 상태를 유지한다.

### 14.2 transfer_to_user()가 바꾸는 것

```text
guest_sessions:
  user_id = 회원 ID
  qr_token_hash = NULL
  expires_at = NULL

SkinAnalysis:
  user_id = 회원 ID
  expires_at = NULL

HairRecRun, FaceAnalysis:
  user_id = 회원 ID
```

분석 결과의 `guest_id`는 그대로 둔다. 이관된 세션은 `find_active_session()`에서 비회원으로 인정하지 않는다.

[결정 기록] QR을 지워 공용 화면에 남은 링크로 회원 결과를 계속 조회할 수 없게 하고, 만료를 비워 비회원 정리 배치에서 제외한다.

**주의:** 현재 이관 대상에는 `HairRender`가 없다. 탈퇴·정리 목록에 HairRender가 있다는 사실과 이관 여부를 혼동하면 안 된다. 스튜디오 결과의 회원 귀속과 보관 정책은 별도 검토가 필요하다.

### 14.3 기존 회원 로그인과 신규 가입의 차이

가입 라우트는 비회원 결과 이관을 호출하지만, 기존 회원 이메일·Google 로그인은 `auth.login()`만 호출한다. **비회원으로 분석하다 기존 계정으로 로그인했다고 자동 이관되는 것은 아니다.** 기존 회원은 제공된 QR claim API를 통해 이관할 수 있으나 일반 화면에서는 해당 UI가 제거된 이력이 있다.

### 14.4 QR claim

`GET /api/qr/{token}`은 로그인 없이 비회원 결과를 조회한다. QR 원문을 해시로 찾아 유효 세션인지 검사한다. 없는·만료·이관된 링크 모두 같은 404를 반환한다. 응답에서 피부 결과의 `image_id`를 비운다.

`POST /api/qr/{token}/claim`은 회원 인증이 필요하고 같은 이관 함수를 호출한다. 이후 같은 QR은 더 이상 조회할 수 없다. 현재 QR 조회의 hair는 응답 기본 빈 목록이며 헤어 결과 조회가 완성된 것으로 볼 수 없다.

[해설] QR 토큰을 가진 사람이 결과를 조회할 수 있는 구조이므로 이 토큰은 단순 표시용 번호와 다르다.

## 15. 사용량 제한과 정리 배치

### 15.1 제한 계산

`services/quota.py`는 별도 카운터 테이블 대신 결과 테이블의 한국 시간 오늘 행 수를 센다.

| 기능 | 기본 비회원 한도 | 집계 |
|---|---|---|
| skin | 3 | SkinAnalysis |
| hair | 3 | HairRecRun |
| studio | 2 | HairRender, failed 제외 |

회원·키오스크는 이 로직에서 제한 없음이다. IP 기준 기본 상한은 기능별 30이며 같은 IP 해시를 가진 세션들을 합산한다. 개별 기능 한도 0이면 현재 함수는 제한 없음으로 빠지므로 그 기능의 IP 검사도 실행하지 않는다.

[결정 기록] 결과 테이블을 세면 카운터 동기화가 필요 없어 단순하다. 한국 자정 기준을 사용하고, 동시 요청으로 한도를 조금 넘는 문제는 복잡한 잠금을 도입하지 않기로 했다.

**1단계 반영:** studio뿐 아니라 피부 생성의 JSON·사진 경로와 헤어 얼굴형 생성·추천 실행에도 quota 검사를 연결했다. 헤어 사용량은 기존 정책대로 HairRecRun을 세므로 사진 장수나 얼굴형 생성 자체를 별도 차감하지 않는다.

### 15.2 매일 정리

FastAPI lifespan에서 APScheduler를 시작하고 매일 오전 4시 KST에 정리한다. 만료 비회원 세션의 결과를 먼저 삭제하고 세션을 삭제한다. 만료 리프레시 토큰과 인증 코드도 지운다.

[결정 기록] 분석 테이블에 세션 FK가 없어 직접 삭제해야 하며, 사용자가 적은 시간에 실행하고 별도 cron 컨테이너를 늘리지 않으려는 선택이다. 시간대는 고정 +09:00으로 만들어 tzdata 의존을 줄인다.

[코드 확인] 현재 cleanup은 스튜디오 보관 정리 `cleanup_renders()`도 별도로 호출한다. “회원에게 이관된 세션은 비회원 만료 삭제에서 제외”와 “모든 종류의 결과 파일이 영구 보관”은 같은 말이 아니다.

## 16. 마이페이지와 회원 탈퇴

### 16.1 내 정보 조회·변경

`GET /api/me`는 이메일·언어·국적·한국 거주 여부·Google 연결 여부를 돌려준다. `PATCH /api/me`는 언어만 변경한다.

[결정 기록] 수정 범위는 명세에 따라 언어로 제한했다. 모델에 칼럼이 있다고 아무 필드나 수정할 수 있는 것은 아니다.

마이페이지의 `_get_user()`는 DB에서 회원을 다시 조회한다. [결정 기록] 탈퇴 후에도 남아 있을 수 있는 액세스 JWT를 막기 위해서다. JWT는 서명이 맞고 만료 전이면 DB 회원 삭제 사실을 스스로 알 수 없다.

### 16.2 탈퇴의 실제 삭제 순서

`DELETE /api/me`:

1. require_user와 `_get_user()`로 실제 회원 확인.
2. 같은 이메일의 진행 중 인증 코드 삭제.
3. `SkinAnalysis`, `HairRender`, `HairRecRun`, `FaceAnalysis`를 user_id로 직접 삭제.
4. User 삭제.
5. 회원 FK CASCADE로 동의 이력·리프레시 토큰·회원 연결 비회원 세션 삭제.
6. 커밋 후 액세스·리프레시 쿠키 삭제, 204 반환.

[결정 기록] 분석 결과에는 회원 FK가 없는 부분이 있어 직접 삭제한다. 선택 동의 이력도 현재 정책상 회원과 함께 삭제한다. 법적 보관 의무를 검증한 문서로 해석하면 안 된다.

탈퇴 API 자체는 비밀번호나 인증 코드 재확인을 하지 않는다. 2단계에서 계정 화면에 삭제 안내와 확인 체크박스·취소 버튼을 추가했다. 확인 체크 후에만 탈퇴 API를 호출하며, 성공 후 onLogout 콜백으로 상위 화면의 결과를 초기화하고 actor를 다시 조회한다. 실패 시 기존 계정·분석 결과는 유지한다.

DB 행 삭제와 S3·로컬 파일 삭제는 다른 작업이다. 현재 delete_user는 파일 저장소 객체를 직접 제거하지 않는다. 기존 문서의 “사진을 저장하지 않는다”는 초기 전제만으로 현재 프로젝트의 모든 이미지·합성 파일이 정리된다고 단정하면 안 된다.

### 16.3 로그아웃과 탈퇴의 차이

로그아웃은 현재 리프레시 토큰 행과 인증 쿠키만 지운다. 계정·동의 이력·분석 결과는 남는다. guest_id 쿠키도 유지한다.

탈퇴는 회원 데이터와 연결된 결과를 삭제한다. 다른 기기의 리프레시 토큰도 회원 CASCADE로 삭제된다. 현재 get_actor는 DB 회원 존재도 확인하므로 탈퇴한 회원의 JWT를 거절한다. 로그아웃은 회원 자체를 삭제하지 않으므로, 별도로 복사된 액세스 JWT 자체를 블랙리스트에 올리는 효과는 없다.

### 16.4 내 분석 이력 — 3단계 추가

`GET /api/me/analyses?kind=all&limit=20&offset=0`은 로그인 회원의 피부 분석과 헤어 추천 실행을 합쳐 최신순으로 반환한다. kind는 all/skin/hair, limit은 1~50, offset은 0 이상이다. user_id를 요청으로 받지 않고 actor에서 가져온다.

각 테이블에 회원 소유자 조건을 먼저 적용하고 UNION ALL로 합친다. 시간 내림차순·종류·ID 내림차순을 사용해 같은 시각과 서로 다른 테이블의 같은 ID도 안정적으로 정렬한다. DB에서 limit+1개만 읽고 has_more로 다음 페이지 여부를 알려준다. 전체 행 수는 계산하지 않는다.

프론트 `AccountHistory`는 계정 화면에서 서버 목록을 조회하고, 선택 시 1단계의 소유자 검사를 적용한 기존 피부·헤어 상세 API를 호출한다. 목록은 기록 종류·번호·날짜만 포함한다. 화면 새로고침 후에도 서버에 남은 회원 기록을 다시 조회할 수 있다. 날짜 표시는 한국 시간이다.

필터·페이지 변경과 화면 이탈 때 이전 요청을 취소하고, 취소 신호를 확인해 늦은 응답이 새 상태를 덮어쓰지 못하게 한다. 빈 목록·조회 실패·상세 결과 삭제에 대한 안내와 재시도를 제공한다. 탈퇴·로그아웃 시 계정 화면에서 이력 컴포넌트도 제거된다.

이력 범위는 SkinAnalysis와 HairRecRun이다. 헤어 추천까지 완료하지 않은 얼굴형 분석, AI 합성 파일, 저장하지 않은 화장품 추천 응답, 소유자가 없는 과거 결과까지 복구하는 기능은 아니다.

## 19. 현재 코드의 중요한 통합 제약

### 19.1 피부·헤어 연동: 작업 전과 현재

작업 전에는 피부 생성이 body의 guest_id를, 헤어 생성이 body/Form의 user_id·guest_id를 받아 저장했다. 현재는 생성 API에 `require_analysis_actor`를 연결하고 서버 actor에서 소유자를 가져온다. JSON 소유자 필드는 호환용으로 남겼지만 저장에 사용하지 않으며, 헤어 사진 Form에서는 소유자 입력을 제거했다.

피부·얼굴형·헤어 추천 결과 조회와 기존 얼굴형을 이용한 추천 실행은 소유권을 검사한다. 회원에게 이관된 결과는 회원 소유자를 우선하므로, 남아 있는 예전 guest_id만으로는 접근할 수 없다. 수분 측정 저장·재시도 응답도 같은 검사를 거친다.

현재 프론트는 이미 same-origin 쿠키를 전송하고 있어 API 주소와 응답 형식을 유지한 채 연동했다. 로그인하거나 촬영 동의로 세션을 시작한 뒤 분석해야 한다. 과거에 소유자 없이 저장한 결과를 자동으로 특정 회원에게 귀속시키지는 않는다.

일반 이미지 업로드·이미지 ID 사용 권한, 스튜디오 결과 이관과 스튜디오 이력은 별도 후속 범위다. 선택 동의·탈퇴 UI는 2단계, 피부·헤어 추천 이력은 3단계에서 연결했다. 이 변경이 모든 API의 권한 검토 완료를 뜻하지 않는다.

### 19.2 탈퇴 직후 남은 토큰

1단계에서 `get_actor()`에 DB 회원 존재 검사를 추가했다. 이제 서명이 유효하더라도 탈퇴한 회원이면 401이다. `require_user`·`require_analysis_actor`를 사용하는 경로에도 적용된다. 대가로 회원 요청마다 User 조회가 추가되므로, 초기 설계의 “액세스 인증은 DB 조회 없음”에서 변경된 지점이다.

### 19.3 동시 요청

이메일 코드 검증·재발급, refresh 회전, QR claim에서 명시적 행 잠금은 확인되지 않는다. 순차 요청에서의 일회성 동작과 동시 요청에서도 엄격히 한 번만 실행되는 보장은 구분해야 한다. 이 문서는 취약점 악용을 실험한 결과가 아니라 코드 구조상 검토할 지점이다.

### 19.4 개발 설정은 운영 기능과 다르다

`DEV_LOGIN=true`면 개발 로그인 라우트가 등록되고 응답에 dev_code가 노출될 수 있다. false면 main에서 개발 라우트를 등록하지 않는다. 이는 테스트 편의를 위해 인증을 우회하는 별도 기능이다.

현재 기본 비밀키는 개발용 문자열이고 cookie_secure는 false다. 기존 문서는 배포 시 키 교체·Secure 활성화·개발 로그인 비활성화를 명시한다. 이 문서 작성 중 실제 .env의 비밀값은 확인하거나 옮기지 않았다.

## 20. 테스트 자료를 읽는 방법

[프론트 API 클라이언트 테스트](../frontend/scripts/test-api-client.mjs)는 다음을 검증하는 코드가 있다.

- JSON·FormData 요청 헤더와 same-origin 설정.
- 204 빈 응답 처리, 서버 오류·422 오류 메시지 변환.
- 두 요청의 동시 401을 하나의 refresh로 처리.
- refresh 실패 시 원래 요청을 무리하게 재시도하지 않음.
- auth 경로 자체 401을 refresh 대상으로 삼지 않음.
- 재시도 401에서 무한 반복하지 않음.
- 갱신 중 취소된 요청의 재시도 방지.
- 늦게 도착한 401의 기존 갱신 결과 재사용.
- refresh 401에 만료 이벤트, 503에는 만료 이벤트를 보내지 않음.

기존 `jy-docs/account-spec.md`·plan에는 계정 통합 테스트와 Google 실계정 테스트 기록이 있다. 이는 작성 당시 기록이다. **이 문서를 만들면서 운영 DB·Google 로그인·이메일 발송 테스트를 새로 수행한 것은 아니다.** 과거 통과 기록과 현재 실행 검증 결과를 구분한다.

DB를 쓰는 계정 테스트·시드·마이그레이션은 데이터를 바꿀 수 있다. 학습 문서 작성에는 실행하지 않았다. 특히 최초 계정 마이그레이션에는 이전 단수형 테이블을 DROP하는 코드가 있어 단순 조회 명령으로 생각하면 안 된다.

## 21. 추천 학습 순서

1. `models/account.py`에서 User·RefreshToken·EmailVerification 관계를 읽는다.
2. `schemas/account.py`에서 요청과 DB 모델이 어떻게 다른지 비교한다.
3. 이메일 send → issue_code → hash_email_code를 따라간다.
4. 이메일 verify에서 실패 후 commit의 위치를 확인한다.
5. auth.login → issue_tokens → set_auth_cookies를 따라간다.
6. get_actor에서 만료 access가 왜 비회원으로 넘어가지 않는지 설명해 본다.
7. 프론트 api()의 401 → refresh → 1회 재시도를 읽는다.
8. signup의 flush와 commit 사이에서 어떤 변경이 묶이는지 적어 본다.
9. Google 인증 후 이메일 인증과 어느 함수부터 공통화되는지 찾는다.
10. guest 이관·consent 변경·delete_user로 데이터 생명주기를 완성한다.
11. studio와 skin/hair의 actor 연결, 공통 소유권 검사, 회귀 테스트를 비교해 통합 방식을 이해한다.

### 스스로 답해 볼 질문

- 액세스 쿠키를 JWT 만료와 함께 지우면 왜 이 프로젝트에서는 문제가 되는가?
- 인증 코드가 틀렸는데 왜 DB commit이 필요한가?
- 가입 토큰과 액세스 토큰을 type으로 구분하지 않으면 어떤 역할 혼동이 생기는가?
- 회원 중복을 미리 조회했는데도 UNIQUE가 필요한 이유는 무엇인가?
- flush 뒤에 회원 ID를 쓸 수 있어도 아직 가입이 확정된 것은 아닌 이유는?
- Google 이메일 인증 여부를 확인하지 않고 기존 이메일 회원에 연결하면 왜 위험한가?
- 비회원 세션을 회원으로 이관할 때 QR과 만료를 모두 지우는 이유는?
- 프론트 Promise 공유가 서로 다른 탭의 동시 갱신까지 해결하는가?
- 로그아웃·탈퇴·프론트 결과 초기화는 각각 무엇을 지우는가?
- API가 있다는 사실과 화면에 연결돼 있다는 사실은 어떻게 다른가?

## 22. 구현 의도를 설명하는 예시

> BOA는 이메일 일회용 코드와 Google 인증을 사용하고, 신규 사용자는 인증과 실제 가입을 분리했습니다. 인증 성공 시 짧은 가입 토큰을 발급하고, 가입 API에서 현재 약관과 추가 정보를 검증합니다. 회원 생성·동의 이력·비회원 결과 이관·로그인 토큰 저장은 한 DB 트랜잭션으로 처리합니다. 일반 인증은 15분 JWT와 DB에 해시로 저장하는 30일 리프레시 토큰을 사용하며, 현재는 탈퇴한 회원을 거절하기 위해 회원 존재도 조회합니다. 만료된 회원이 비회원으로 잘못 분류되지 않도록 액세스 쿠키는 JWT보다 오래 유지하고, 서버의 401을 받은 프론트가 갱신 후 한 번 재시도합니다. 피부·헤어 소유자 저장과 조회 제한, 비회원 사용량 제한은 1단계에서 연결했습니다. 선택 동의·탈퇴 UI는 2단계, 피부 분석·헤어 추천의 회원 이력 조회는 3단계에서 연결했으며, 실제 메일 발송과 스튜디오 이력 등은 후속 작업입니다.
