# 계정 모듈 설계 결정

담당: GangJiyeon · 기준: 2026-11-26 코드

계정 모듈(로그인·가입·비회원·QR·키오스크·탈퇴)을 만들면서 **무엇을 정했고 왜 그렇게 했는지** 정리한 문서. API와 테이블은 [account-api.md](account-api.md), 코드 흐름 설명은 [account-study-guide.md](account-study-guide.md)

## 한눈에 보기

| 문제 | 선택 | 핵심 이유 |
|---|---|---|
| 다른 파트가 결과 소유자를 어떻게 아는가 | `get_actor()` 하나로 회원·비회원·키오스크·익명 판별 | 피부·헤어 파트는 `Depends` 한 줄로 연결, 판별 규칙은 한 곳에만 |
| 로그인 유지 | JWT 액세스 15분 + 리프레시 30일(갱신마다 교체) | 액세스는 DB 조회 없이 검증, 탈취돼도 피해 시간 짧음 |
| 토큰 보관 위치 | 전부 httpOnly 쿠키, 프론트는 `GET /api/actor`로 상태 확인 | JS에서 토큰을 읽을 수 없어 XSS로 탈취 불가 |
| 로그인 수단 | Google만 (이메일 코드 로그인은 11월에 제거) | 비밀번호·메일 발송 없이 본인 확인을 Google에 맡김 |
| 비회원도 써볼 수 있게 | 촬영 동의 후 7일짜리 비회원 세션, 기능별 하루 횟수 제한 | 가입 없이 체험, AI 호출 비용은 상한으로 관리 |
| 비회원 결과를 잃지 않게 | 가입·QR 저장 시 결과를 회원에게 이관 | 체험 → 가입 흐름에서 결과 유지 |
| 공용 태블릿(행사장) | 관리자 코드로 등록한 키오스크, 사용자마다 새 세션 | 앞 사람 결과·로그인과 섞이지 않게 |
| 개인정보 | 얼굴 원본 미저장, IP는 HMAC, 토큰은 해시만 저장 | DB가 유출돼도 원문을 복원할 수 없게 |

## 1. 공통

| 결정 | 이유 |
|---|---|
| 테이블 규칙은 피부 파트와 통일 (복수형, 기본키 `id`, Alembic) | main에 먼저 머지된 피부 테이블과 같은 방식. 팀 SQL의 단수형 계정 테이블은 사용 안 함 |
| 마이그레이션에서 예전 단수형 계정 테이블 삭제 (IF EXISTS) | `terms` 이름이 겹쳐서 팀원 DB에서 생성 실패. 예전 테이블은 코드에서 안 쓰던 빈 테이블 |
| 외부 설정이 없으면 503 (Google, 관리자 코드) | 설정 누락을 500 대신 명확한 상태로 표시 |
| 약관 시드는 고정 날짜(2026-09-01) | 팀원 DB마다 같은 값 |

## 2. 요청자 판별

| 결정 | 이유 |
|---|---|
| `get_actor()`를 가장 먼저 구현 | 피부·헤어 파트가 결과에 `user_id`/`guest_id`를 넣으려면 필요 → 다른 파트가 막히지 않게 |
| 판별 순서: 키오스크 → 회원 → 비회원 → 익명 | 공용 기기에 남은 로그인 쿠키보다 기기 모드가 우선 |
| `require_analysis_actor()` 공통 제공 (익명이면 403) | 파트마다 익명 처리가 달라지는 것 방지 |
| `GET /api/actor` 추가 | 인증 쿠키가 httpOnly라 프론트가 직접 못 읽음 |
| 쿠키는 `request.cookies`에서 읽음 | `Cookie()` 파라미터를 쓰면 Swagger에 입력칸이 생겨서 헷갈림 |
| 액세스 토큰이 있는데 만료·위조·탈퇴 회원이면 401 | 비회원으로 넘기면 회원의 분석 결과가 비회원 쪽에 저장될 수 있음 → 프론트가 refresh 후 재요청 |

## 3. 토큰과 쿠키

| 결정 | 이유 |
|---|---|
| 액세스 JWT 15분 + 리프레시 30일 | 포트폴리오용으로 표준 구조 선택 (단순한 서버 세션 방식도 검토) |
| 리프레시 토큰은 갱신마다 교체, 예전 토큰은 거부 | 탈취된 토큰을 오래 못 씀. 재사용 탐지·전체 기기 로그아웃은 범위 밖 |
| 액세스 쿠키는 30일 유지 (토큰은 15분) | 쿠키가 먼저 사라지면 "만료"가 아니라 "비로그인"으로 보여서 위의 401이 동작 안 함 |
| 리프레시 쿠키 path `/api/auth` | 갱신·로그아웃 요청에만 전송 |
| refresh 실패 시 인증 쿠키 삭제 | 안 지우면 만료된 액세스 토큰 때문에 계속 401 |
| 여러 탭의 refresh를 한 번에 하나만 (Web Locks) | 탭 두 개가 동시에 갱신하면 한쪽이 교체 전 토큰을 보내 로그아웃되던 문제 |
| 토큰에 `type`(access/signup) 넣고 검증 | 가입 토큰을 액세스 토큰으로 쓰는 것 방지 |
| 쿠키 expires를 UTC로 변환 | DB 시각이 +09로 와서 쿠키 설정 시 500 → 테스트 중 발견해서 수정 |
| `SameSite=Lax`, `Secure`는 환경변수 | Safari가 http://localhost에서 Secure 쿠키를 막음 → 로컬 false, 배포 true |

## 4. Google 로그인

| 결정 | 이유 |
|---|---|
| ID 토큰을 Google 공개키로 서명까지 검증 (`pyjwt[crypto]`) | 내용만 디코딩하면 위조 토큰 통과 |
| 발급자·대상 앱(client_id)·만료·`email_verified` 모두 확인 | 다른 앱용 토큰이나 미인증 이메일로 남의 계정에 연결되는 것 방지 |
| 회원 찾기 순서: `google_sub` → 같은 이메일 | `google_sub`는 Google 계정 고유값이라 우선 |
| 같은 이메일이 다른 Google 계정과 이미 연결돼 있으면 409 | 계정 탈취·혼동 방지 |
| 처음 로그인이면 회원을 바로 만들지 않고 가입 토큰(JWT 10분) 발급 | 약관 동의 없이 회원이 생기지 않게 |
| 이메일은 소문자로 정규화 | `Jiyeon@` = `jiyeon@` |
| 개발용 `dev-login`, `google/dev-start` (`DEV_LOGIN=true`일 때만 라우트 등록) | Swagger만으로 테스트. 꺼지면 라우트 자체가 없음 |

## 5. 가입과 약관

| 결정 | 이유 |
|---|---|
| 약관 6종: 필수 SERVICE·PRIVACY·AGE_14·FACE_IMAGE, 선택 PHOTO_STORAGE·MARKETING | DB에는 종류·버전·필수 여부만, 본문은 프론트 |
| FACE_IMAGE를 가입 필수 약관에 포함 | 회원은 가입 때 이미 동의 → 촬영 전 동의 단계 불필요 |
| 없는 약관 id·옛 버전 id는 400 | 어떤 버전에 동의했는지가 기록의 핵심 |
| 필수 약관 누락 시 메시지에 종류 표시 | 프론트를 우회한 직접 호출도 서버에서 차단 |
| 회원 생성 + 동의 이력 + 결과 이관 + 로그인을 한 트랜잭션 | 중간에 실패하면 반쪽짜리 회원이 남지 않게 |
| 이메일 중복은 미리 확인 + `IntegrityError`도 409 | 동시 가입은 미리 확인만으로 못 막음 → DB UNIQUE가 최종 방어 |
| 동의는 이력 테이블에 추가만 (수정 없음) | 언제 어떤 버전에 동의·철회했는지 남김. 최신 행이 현재 상태 |
| 같은 상태로 다시 요청하면 기록 추가 안 함 | 이력에 의미 있는 변화만 |
| 필수 약관 철회는 400 + 탈퇴 안내 | 필수 약관 철회 = 서비스 이용 불가 |

## 6. 비회원과 사용량 제한

| 결정 | 이유 |
|---|---|
| 웹 비회원 세션은 쿠키당 1개, 7일 | 결과 보관 기간 약속 |
| 세션 재사용 시 QR 토큰만 새로 발급, 만료 시각은 그대로 | DB에 해시만 있어 예전 원문을 다시 줄 수 없음. 만료를 연장하면 7일 제한이 무의미 |
| 피부 3회 · 헤어 추천 3회 · AI 헤어 합성 2회 (하루, 기능별 설정, 0이면 끔) | 합치면 금방 막힘. 합성은 외부 AI 비용이 있어 더 낮게 |
| 헤어 추천은 요청 1번(사진 3장) = 1회 | 장마다 세면 한 번에 다 씀 |
| 합성 실패는 횟수에서 제외 | 사용자 탓이 아닌 실패로 기회를 잃지 않게 |
| 별도 카운터 없이 결과 테이블의 오늘 행 수를 셈 | 테이블·동기화 추가 없이 단순 |
| 하루 기준은 한국 시간 자정 | 서버 시간대와 무관 |
| 같은 IP 세션 합산 상한 30회 (0이면 끔) | 쿠키를 지우고 다시 오는 경우 차단. 행사장은 모두 같은 IP라 0 |
| 429에 `code` 포함 (`GUEST_DAILY_LIMIT` / `IP_DAILY_LIMIT`) | 프론트가 가입 유도와 단순 안내를 구분 |
| 동시 요청으로 1회 더 되는 경우는 허용 | 피해가 작고, 막으려면 분석 코드와 잠금을 맞춰야 함 |
| IP는 HMAC으로만 저장 | 같은 IP끼리 비교만 하면 되니 원문 불필요 |

## 7. QR과 결과 이관

| 결정 | 이유 |
|---|---|
| 이관은 `transfer_to_user()` 하나 (가입·QR 저장 공통) | 같은 규칙을 두 곳에 복사하지 않게 |
| 이관 대상: 피부 분석, 얼굴형 분석, 헤어 추천, AI 합성 결과 | 가입 직후 체험 결과가 404가 되지 않게 |
| 이관하면 QR 토큰·만료 시각 비움 | 키오스크 화면의 QR로 다른 사람이 회원 결과를 계속 보는 것 방지, 만료 배치 대상에서 제외 |
| QR 조회 응답은 피부 파트 `AnalysisRead` 재사용, `image_id`만 비움 | 화면마다 같은 형식. 사진으로 이어지는 단서 제거 |
| 없는·만료·이관된 링크 모두 404 하나 | 토큰 존재 여부를 외부에 알리지 않음 |

## 8. 키오스크

| 결정 | 이유 |
|---|---|
| 해제·위조된 키오스크 토큰은 무시하고 다음 판별로 | 해제된 기기는 일반 비회원 취급 (횟수 제한도 다시 적용) |
| 이 기기에서 시작한 세션만 키오스크 세션으로 인정 | 웹 비회원 쿠키가 섞여도 다른 사람 결과에 저장되지 않게 |
| 세션 없는 키오스크는 분석 403 | 동의 전 촬영 방지 |
| 사용자마다 항상 새 세션, IP 저장 안 함, 횟수 제한 없음 | QR 한 장에 그 사람 결과만. 공용 기기라 IP 상한 의미 없음 |
| 종료는 세션 쿠키만 삭제 | 결과는 남아서 QR로 계속 조회·저장 가능 |
| 관리자 코드는 시간 일정 비교 | 응답 시간으로 코드 추측 방지 |
| 키오스크 쿠키 400일 (브라우저 최대) | 해제 전까지 유지 |
| 같은 기기 재등록 시 이전 등록 자동 해제, 기존 비회원 쿠키 삭제 | 주인 없는 활성 기기·이전 세션이 남지 않게 |

## 9. 탈퇴와 만료 정리

| 결정 | 이유 |
|---|---|
| 탈퇴 시 분석 결과를 직접 삭제 후 회원 삭제 | 결과 테이블에 회원 FK가 없어 CASCADE 안 됨. 동의 이력·리프레시 토큰·세션은 users CASCADE |
| 탈퇴는 로그인만 확인, 재인증 없음 | 확인 체크는 프론트. 캡스톤 규모 |
| 얼굴 원본 사진 저장 안 함 | 소유자 칼럼이 없으면 탈퇴·만료 때 지울 대상을 찾을 수 없음 |
| 매일 새벽 4시(KST) 정리 배치: 만료 비회원 세션과 결과, 만료 리프레시 토큰, 오래된 합성 이미지 | 7일 보관 약속을 실제로 지킴 |
| APScheduler를 서버 안에서 실행 (FastAPI lifespan) + 수동 스크립트 | 별도 cron 컨테이너 불필요, 스크립트로 바로 테스트 |
| 서버 여러 대면 중복 실행돼도 그대로 둠 | 만료 데이터 삭제는 여러 번 해도 결과가 같음 |

## 남은 한계

- 리프레시 토큰 재사용 탐지·전체 기기 로그아웃 없음
- PHOTO_STORAGE 철회 시 생성 이미지 삭제는 미구현 (동의 이력만 변경)
- 약관 본문 미연결 (가입 화면에 "준비 중" 표시)
- 프록시 뒤 배포 시 IP를 `X-Forwarded-For`로 받으려면 uvicorn `--proxy-headers` 필요
