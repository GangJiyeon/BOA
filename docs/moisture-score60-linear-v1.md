# BOA 수분 지수 0~60 / 6단계 업데이트

새 센서 측정의 최종 계산값·DB 저장값·화면 값은 모두 **0부터 60까지의 정수**다.
10의 배수만 출력하지 않는다. 0, 1, 2, …, 59, 60을 모두 표현한다.
추천 정책은 이 정수의 6단계에서 결정한다.

## 적용 순서 — Windows 노트북

1. 현재 BOA-git 폴더를 복사해 백업한다. 이 ZIP은 최신 수분 추정기/추천 통합본에 덮어쓰는 변경분이다.
2. ZIP을 임시 폴더에 풀고, `backend`, `frontend`, `hardware`, `fixtures` 폴더를 실제 BOA-git 안으로 복사한다. 같은 이름 파일은 교체한다.
3. Arduino IDE에서 `hardware/arduino/moisture_sensor/moisture_sensor.ino`를 열어 UNO R4 WiFi에 업로드한다. 같은 폴더에 새 **MoistureScore60.h**와 기존 Fdc2112.h, MoistureBle.h가 있어야 한다. ArduinoBLE 라이브러리를 사용한다.
4. 시리얼 모니터 115200에서 `BOA firmware: moisture-score60-v16`을 확인한다. 부팅할 때 센서에서 손과 피부를 떼어 둔다.
5. PowerShell:

```powershell
cd C:\Users\sbyun_2\Desktop\BOA-git\backend
docker compose up -d --build api
```

6. 프론트 터미널에서 기존 서버를 Ctrl+C로 종료하고:

```powershell
cd C:\Users\sbyun_2\Desktop\BOA-git\frontend
npm.cmd run dev
```

7. 브라우저를 새로고침하고 측정기를 다시 연결한다. 기준값 보정 후 피부에 한 번 접촉해 3초간 유지한다. 새 결과에 `/60`과 `1/6단계` 같은 상태가 표시된다. 측정 상세의 앱 표시는 `moisture-score60-v1`이다.
8. 사진 분석 후 추천을 실행한다. 측정 화면과 추천 결과의 수분 지수가 같은지 확인한다.

이 업데이트 자체에는 추가 DB 마이그레이션이나 추천 규칙 재시드가 없다. 기존 수분 관측 테이블과 35개 규칙을 사용하는 통합본이 선행 조건이다. 개인 `.env`, Compose 파일(노트북의 5433 포트 설정 포함), DB 데이터는 이 패키지에 포함하지 않는다.

## 최종 지수·등급·추천의 계약

| 최종 정수 지수 | 6단계 | 이름 | 기존 추천 정책 |
|---|---|---|---|
| 0~9 | 1 | 매우 부족 | 부족 / 개선 필요 |
| 10~19 | 2 | 부족 | 부족 / 개선 필요 |
| 20~29 | 3 | 보통 중 낮음 | 보통 / 유지 |
| 30~39 | 4 | 보통 | 보통 / 유지 |
| 40~49 | 5 | 보통 중 높음 | 보통 / 유지 |
| 50~60 | 6 | 매우 높음 | 충분 / 유지 |

경계 **10·20·30·40·50은 다음 단계의 시작값**이다. 단계는 겹치지 않는다. 60은 6단계에 포함된다. ‘매우 높음’은 원문의 Very High를 옮긴 표현이며 지성·유분 과다 판정이 아니다.

0은 유효한 접촉의 작은 반응에서 나올 수 있다. 미접촉·센서 오류·표본 부족은 0으로 바꾸지 않고 기존처럼 미측정/실패로 처리한다. 6단계가 표시된다는 것은 6가지 서로 다른 제품 효능이 검증됐다는 뜻이 아니다. 기존 부족/보통/충분의 추천 규칙과 선택적 제외를 유지한다.

## 계산 방법과 경계의 이유

제조사 구형 드라이버는 `(공기 기준 - 접촉값) × 100 / 공기 기준`을 정수 나눗셈으로 계산한다. 예를 들어 0.9는 0, 12.9는 12다. PNJ 부록은 그 정수에 <=12, <=22, <=27, <=39, <=45, <=100의 경계를 적용한다.

BOA는 최종 점수를 더 자세히 표현하기 위해 비율 계산의 소수점을 환산 전까지 유지한다. 따라서 원문의 **정수 버림 분류**와 같은 등급을 얻는 연속 반응 경계는 **13, 23, 28, 40, 46**이다. 12.9는 여전히 첫 단계이며, 13.0부터 두 번째다.

반응 구간 시작 `a`, 끝 `b`, 0부터 시작하는 단계 번호 `k`에 대해:

```text
원래 연속 반응 경계: [0, 13, 23, 28, 40, 46, 100]
최종 점수 = 10*k + min(9, floor(10*(반응-a)/(b-a)))
반응이 정확히 100이면 최종 점수는 60
등급 = min(6, floor(최종 점수/10)+1)
```

반올림으로 다음 단계로 넘어가지 않게 구간 내부에서 버림을 사용한다. 부동소수점 경계 오차만 1e-9 이내에서 보정한다. 이 0~60 환산은 BOA의 표현 설계이며 PNJ나 제조사가 제공한 60점 척도가 아니다.

센서 설정 환산은 기존 gain16, OFFSET170, FIN2와 장치가 읽어 전송한 reference divider 11/22/44를 사용한다. 공기 기준 B, 마지막 1초 중앙값 X, 실제 분주비 D에 대해:

```text
B_ref = (B+170)*11/D - 170
X_ref = (X+170)*11/D - 170
연속 반응 = 100*(B_ref-X_ref)/B_ref
```

이는 구형 제조사 드라이버의 x10 인자가 실제 0x200B(divider11)가 되는 동작을 기준으로 한 기존 설정 환산이다. 논문이 사용한 Arduino 포트 구현과 완전히 동일함을 확인한 것은 아니다. 이 전기적 환산은 실제 피부 수분 함량의 교정식이 아니다.

## 데이터 및 코드 변경

- 새 척도 버전: `boa-moisture-60-v1`. 저장 payload에 버전을 넣고 서버가 원시 표본에서 다시 계산한다.
- 응답에 `normalized_score`(0~60), `score_max=60`, `moisture_level`(1~6), `moisture_level_label`을 제공한다.
- 새 척도에서는 최종 정수 점수에서 등급과 추천 카테고리를 계산한다. 브라우저가 보내는 다른 점수·라벨로 저장된 센서 판정을 바꿀 수 없다.
- 수분 측정→사진 분석→추천 요청은 분석 ID와 측정 ID를 함께 보내며, 기존 DB의 0~100 구간에 새 센서 점수를 잘못 대입하지 않는다.
- 기존 `boa-capacitance-display-v2` 등 과거 기록은 자동 재환산하지 않는다. 이전 결과는 `/100`, 새 측정은 `/60`으로 구분한다. 기존 수동 입력 기능은 구형 0~100 계약이므로 UI에 명시했고, 새 센서 지수를 수동 입력 칸에 넣지 않는다.
- 아두이노는 원시값과 실제 설정을 BLE v5로 계속 전송한다. 고정 3초의 마지막 1초 중앙값을 사용한 **최종 결과는 프론트와 서버가 동일 계산식으로 계산**한다. 펌웨어의 `instant_score60`·`instant_level6` 시리얼 출력은 현재 표본의 진단값이며 최종 3초 결과가 아니다. BLE 샘플을 미리 정수 점수로 바꿔 정밀도를 잃지 않는다.
- 단일 접촉, 고정 3초, 마지막 1초의 중앙값, 경고 처리와 1회 종료 동작은 유지한다.

## 검증 및 제한

검증한 코드 기준:

- 백엔드 전체 229개 테스트 통과: 6단계 저장/조회/추천, 0점과 60점 저장, 중복 저장, 클라이언트 변조 무시, 기존 척도 보존 포함.
- 0~100 연속 반응 100,001개에서 원문 정수 버림의 6단계와 새 최종 점수 등급이 일치하고, 0~60 모든 정수가 생성됨을 Python/C++로 확인.
- Python/TypeScript 공통 1,012개 환산 사례와 42개 설정 환산 사례 비교. React 결과 카드에서 61개 점수의 `/60`·등급 표시 확인.
- BLE 프로토콜, 자동 측정, 실제 과거 기록의 소프트웨어 재생, 사진 분석→저장→추천 DOM 시험 및 production 빌드 통과.
- 아두이노 스케치의 C++ 호스트 모형 시험과 새 점수 함수 시험 통과. 실제 UNO R4 타깃 빌드·장치 업로드·접촉 측정은 이 환경에서 수행하지 않았다.

반응이 1점으로 환산되던 기록을 더 높은 점수로 보이도록 올리는 패치는 아니다. 예를 들어 B2538/X2506에 divider44를 가정한 재생은 새 지수 1/60이다. 구형 기록의 실제 분주비가 없는 경우 이 가정은 실제 측정 설정의 확인이 아니다.

분류 기준은 같은 보드를 쓴 PNJ 2023 공개 부록에서 차용한 잠정 정책이다. 그 문서의 앱 코드에는 별도의 3·5 경계도 있으나, 차이를 설명할 비교 실험 본문은 접근 제한이라 확인하지 못했다. 따라서 자체 피부 판정 정확도 검증이나 원문 최종 임상 기준의 완전한 재현을 주장하지 않는다.
